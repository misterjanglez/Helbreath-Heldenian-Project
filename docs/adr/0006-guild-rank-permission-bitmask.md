# Guild ranks are permission bitmasks, not hardcoded role checks

The Phase-2 guild rebuild (design session #93, 2026-08-07) replaces the original's two live ranks (guildmaster 0 / guildsman 12) — whose single-approver shape made every guild function bottleneck on one person being online — with three fixed ranks: **Guildmaster / Officer / Guildsman**. Every guild-gated action (approve joins/leaves, kick, promote, Commander duty, fightzone reservation, Council-channel access, Treasury withdraw, Title management) checks a **permission bit**, and each guild carries a per-rank permission-mask table seeded from fixed defaults — code never asks "is rank 0?", it asks "does this member hold this bit?".

We chose this over (a) hardcoded three-rank checks — which would re-plumb every gate the day configurable ranks are wanted — and (b) shipping a full WoW-style rank editor now — the single biggest client-UI item in the phase. With masks in data from day one, "configurable ranks" later (custom names, checkbox permissions, a fourth tier) is purely an editing dialog: no schema, wire, or handler change. Consequences: Phase 3 consumes *Commander eligibility* as a permission bit plus a Guild-Level slot count (see ADR 0007), superseding the plan §3.2 "guildmaster only" baseline; hardcoded non-bits are only Transfer-mastership and Disband (Guildmaster forever).
