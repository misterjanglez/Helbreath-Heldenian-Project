# The ledger stopped inheriting the log file's opinions

Issue #78 (epic #74, Item Provenance Ledger phase 2.2). #76 built the store and #77 gave it a world to write about; nothing was writing to it. This turns the two existing `item_log()` overloads into a dual sink — the text channels exactly as they were, plus a structured ledger event — and wires creation events from the minting factory. Server 0.19.0 → **0.20.0**; Client stays 0.10.2 and **Compatibility stays 0.9.0**, because Serials still never touch the wire.

- **The ledger half runs before the text half, and that ordering is the whole change.** Each text sink drops what it is not interested in, and there are three of those: an item `check_good_item()` does not consider worth a line (a whitelist of about sixty ids, so *most* items), an action its switch has no case for, and a client handle that no longer resolves. Every one of them is a hole in a log whose only value is not having any — and the worst of the three is the whitelist, because an audit trail missing exactly the ordinary items is missing exactly what a dispute will be about. The filters stay where they were; they just stop deciding for both sinks at once. All three are proved by driving them: the text sink returns `false` and the ledger row is still there.
- **Creation is emitted from the mint, not from the venues.** `stamp_provenance` is the one place a Serial is assigned, so the birth record leaves from the same three lines — "minted ⟹ birth row" is structural rather than a rule that 45 creation sites have to remember. It also settles the two cases that look like creations and are not, for free rather than by a flag: `restore_item` carrying a stored Serial never reaches those lines, and neither does `transform_item`, so a reboot does not re-birth the world and an evolution chain does not split one item's biography in two.
- **A loot birth row reads tier 0, and that is deliberate rather than missed.** An NPC drop creates the item and *then* rolls its attributes onto it, so the tier byte does not exist yet at the moment of minting. The alternative — roll before mint — reorders the drop path's dice draws, which is a balance change wearing an audit change's clothes. Both halves of an NPC drop's birth context, the location and the rolled tier, belong to #79, which already owns the drop-location gap; until then the dropping monster's name reaches the ledger on the drop event instead.
- **GmMint's second handle is a quantity, and the ledger had to be told.** `item_log(action, give_h, recv_h, item)` has a parameter whose meaning depends on another parameter: for a GM mint it carries the minted count, not a player. Read as a handle it would name the wrong player in an audit trail. The event records it as `{"qty":N}` and leaves the counterparty NULL, and the prover pins that by passing a *live client handle* as the quantity — so if the special case is ever tidied away, a real name appears in that column and the check goes red instead of looking plausible.
- **`detail` is written by a JSON library rather than by string concatenation, and the encoder lives next to the column.** One quote in an NPC name out of a content file would otherwise produce a row no reader can parse, and a column of event-specific JSON is only worth having if every row in it parses. `nlohmann` was already vendored and already used by the server, so this is reuse rather than new code; it went into the ledger store's own translation unit — beside the column whose contract it implements, and out of the 6000-line manager. The boot-boundary event, which had been assembling its JSON by concatenation since #76, now goes through the same encoder.
- **`at` is stamped by the store when the caller leaves it 0.** The dual sink records from inside the game action, so "when" is always the moment of the call. Leaving each site to say so puts a clock read at every call site and gives a forgotten one the epoch — which orders before every event ever recorded. `record_mint` still sets it explicitly, because a birth row and its creation event have to share one second, and its creation event now goes through `record_event` as well: the buffer's guards should have one door, not two.
- **`itemlogcheck` is the prover, and it moves the sink instead of cleaning up after itself.** An append-only audit log cannot have its test rows deleted afterwards, so the command swaps a scratch database in as the game's ledger for the duration of the run, restores the live one on every exit path, and asserts the restore rather than trusting it. Two synthetic clients are installed in free handles for the same reason the swap exists: without an actor, "the actor is recorded" could only be tested through its NULL path, which is the half that does not matter. 15 checks covering the birth row, Counted silence in both directions, the Serial key, the event-type passthrough read back as a literal number, actor and counterparty, NULL-not-empty for absent columns, the timestamp, all three text-sink filters, the GmMint quantity and the escaped NPC detail.
- Evidence: **15/15 on Windows and Linux, machine lines sha256 `84947649` on both**. Verified to go red three ways: disabling the dual sink turns 9 of 15 red, disabling the mint emission turns exactly `factory_mints_birth_row` red, and disabling the timestamp stamp turns exactly `timestamp_stamped` red. `serialcheck` `9442eea8`, `ledgercheck` `7092d493`, `gamedbcheck` `d5148aae` and `DROPODDS` `f8e51b4e` are all unchanged — the same values #75/#76/#77 recorded, so nothing in the drop pipeline or the persistence layer moved. `Scripts/check_item_factory.py` green. Windows Server Debug green (only the pre-existing `LNK4098`); Linux green on a full server-subset sync to `~/hb38-ci`, with the build log naming `CmdItemLogCheck.cpp.o` — this cycle adds files and `SERVER_SOURCES` is an explicit list, so a diff-only sync would have produced a green binary with the prover silently absent.
- Worth knowing: the three provers had three byte-identical copies of "delete a scratch database and the two files WAL leaves beside it"; that and the probe-item selection now live in `CheckTally`, the shared scaffold, which is why `ledgercheck` and `gamedbcheck` are byte-identical after being touched. The detail string is now built *after* the event is known to exist, so a stackable NPC drop no longer formats a JSON object it immediately throws away — every gold drop in the world takes that path. Running any prover mints real Serials and therefore now leaves real birth rows in the live ledger; they are honest (the Serial was consumed) and left alone rather than deleted.
- Deliberately not done here: **the Counted tier's flow counters are still unwired** — `record_flow` exists and nothing calls it, so stackables are absent from the ledger rather than aggregated, and their `flow_type` taxonomy is not yet fixed. **`force_item_log` stays**, dead as it is: deleting it makes `by_player` dead too, and voluntary-versus-forced is a distinction the ledger will want as an event rather than a parameter — #79's call, not an audit ticket's. And the deeper fix for the quantity-in-a-handle-slot ambiguity, a separate entry point for GM mints, was left for the ticket that adds the next emitter; D5's framing is to upgrade the sink, not to re-instrument.

# Black text on a black panel, in about a hundred places

The palette inversion that came with the flat panels stopped one colour short, and it was the one most of the dialogs actually drew body text in. Client 0.10.1 → **0.10.2**.

- **`UIBlack` could not be inverted with the rest, so it was left — and it is the default argument of both `put_aligned_string` overloads.** Every other text colour was flipped in place when the panels went dark, because a name like "label" or "disabled" means the same thing on either surface. Black cannot do that: it is also a real black, used for the drop shadows under the HUD numbers, for sprite tint parameters, for the minimap. So it stayed literal — and roughly 170 colourless calls plus 80-odd explicit ones went on drawing near-black text onto a near-black panel. The spellbook and skills dialogs were the worst of it, but so were every shop, bank, city hall and blacksmith screen.
- **The sweep had to tell text apart from the other uses, so it keys on the call, not the colour.** Only lines that actually draw text are rewritten, which is what leaves `DrawParams::tinted_alpha(UIBlack.r, ...)` and the `+1,+1` shadow passes alone. Three exclusions are deliberate and recorded in the script: the menu screens draw on painted parchment where black is correct and white would be unreadable; the HUD panel's blacks are all shadows under white numbers on brass that was never flattened; and the skills dialog maps to *disabled* rather than *label*, because its black meant "you cannot use this" and body-text white would have made every locked skill look available.
- **The bitmap-font links were the same bug wearing a different hat.** `with_highlight` draws a lit edge at colour + (90,55,50) and the body on top, so on parchment the whole `BmpBtn*` family could be near-black and still read — the edge did the work, and the states were told apart by the edge rather than the body. On a dark panel the body disappears and only a muddy edge is left, which is what happened to the NPC dialog's "Next" and the exchange links. The family is inverted with the states genuinely pulled apart now, so resting is dimmer than hover for the first time.
- **The one dialog still on light art keeps dark links, explicitly.** The Slates plate is a carved stone the slates are laid on, so it never got flattened; it now carries its own two colours rather than following a palette that was tuned for the opposite surface.
- **Audited rather than eyeballed.** Every colour a dialog draws text in was scored against the panel: the lowest is now 4.4:1 (the disabled-spell grey, where being dim is the point) and everything else clears 4.7:1. `UIWarningRed` was raised because at 3.2:1 the one colour whose whole job is to be noticed was the hardest to read.
- Windows Debug green for both targets, Release green and deployed.

- **The bag went back to being brass, because "is this a depicted object?" was the wrong question.** Replacing the seam's size heuristic with a per-frame list fixed the crusade map and the alchemy vessels, but it filed the inventory chest with them — and the chest, however much it is drawn as a chest, is the bag dialog's panel: every item slot in that dialog is measured against it. The Slates stone plate and Manufacture's bowl and cauldron are things the dialogs put items **on**, so they stay art; the chest is the surface itself. The wells and the arrows are drawn from primitives now, transcribed off that frame, and both dialogs read one shared layout instead of two copies of the same six numbers. The shop's quantity selector used the same orange plates as the level-up arrows, positioned by their own sprite pivot at coordinates unrelated to the rects its click handler tested; those are themed buttons on their real rects.

# The dialogs stopped being pictures of dialogs

Continuation of the flat-panel UI effort: every in-game dialog now draws its chrome from renderer primitives instead of pak sprites, which is what lets a caption be a string, a button know what it says, and a panel change width. Client 0.9.1 → **0.10.0**; Server and **Compatibility both unchanged**, because none of this touches the wire.

- **The size heuristic that decided what was a panel had been eating artwork.** The transitional seam flattened any dialog-sheet frame of at least 150x60, which is true of every parchment panel — and also true of the inventory chest, the Slates stone plate, the alchemy bowl and cauldron, the level-up dialog's stat grid, the Exchange item wells, and the crusade world map. All of them were being replaced by empty rectangles, the map most visibly: a 279x280 illustration of Aresden and Elvine rendered as a grey box in the Commander, Constructor and Soldier dialogs. Size was never the right question; the seam now carries an explicit per-frame list of what is actually a panel, which also stops it calling `GetFrameRect` on a frame index that does not exist on its sheet. Only the Exchange wells needed redrawing from primitives — they were part of the panel frame, which is why the 58px slot pitch in its draw code had no rectangle anywhere to go with it.
- **Buttons had their captions painted into the art, so converting one meant reading it off a 2001 atlas.** All 32 were transcribed from sheet 10 with their frame numbers recorded beside them, and every in-game dialog plus all five character-screen overlays now call one `draw_button` that takes a rect and a caption. The rect is the point: the frame-pair version drew a fixed 74x20 sprite wherever it was told and hit-tested a rect that only happened to line up, and several were a pixel out. Two footer slots are now stated once and the per-dialog rects alias them, so every dialog's buttons land in the same place by construction. The menu screens deliberately keep their pak buttons — their backgrounds are painted illustrations, not flat panels, and a themed button on painted parchment would look like a mistake.
- **Three buttons stopped lying about their state.** The art had no disabled face, so "you cannot do this yet" could only be said by drawing nothing at all or by withholding the hover frame. Confirm on the majestic stat dialog vanished entirely until you had spent a point; Upgrade drew its idle face when you could not afford it; Sell and Change went quiet without going grey. All four now grey their caption, which is the thing the art could not do.
- **A scroll rail survived the flattening because it was 23 pixels wide.** Six list dialogs drew a vertical brass strip on the right edge of an otherwise flat panel — the one gate the size heuristic let through. The gutter is now the theme's: one rect states the track, and the grab band derives from it rather than being hand-written per dialog at three different sizes. The NPC dialog turned out to have been computing its scroll position every frame and never drawing a thumb, so its scrollbar was invisible while its drag worked.
- **The settings dialog was reading its own layout back out of the art at runtime.** It cached six frame dimensions off the sprite sheet on first update, with a hardcoded fallback set for the frames before the sprites loaded — two of which were simply wrong (280 and 36 against the art's 160 and 32) and never noticed, because the real values won by the second frame. Drawing the boxes from primitives makes those sizes the layout, so they are constants now and the draw and click paths read the same ones. The graphics scrollbar had the same split and it mattered: the drag was mapping against the pak thumb's height while a differently sized thumb was drawn, so the cursor and the thumb tracked at different rates. Ten copies of measure-text-and-centre-it collapsed into one segment drawer, and the volume rows into one.
- **Shift-hovering an item on the ground now tells you what it is, and nothing new had to travel to do it.** The tile already carries the item's full instance data, not just its id, so the floor path was giving you a bare name while holding everything the inventory tooltip prints. The tooltip builder was extracted to take a config row plus an instance — which is exactly what a ground pile is — and both paths now go through it. That surfaced a quieter bug: the mana-save line lived in the tooltip overload that takes a live item, so every caller working from an id and an instance, shop rows included, had been silently dropping it.
- **The character dialog is wider, because a flat panel has no fixed background to be as wide as.** A right-hand pane behind Combat and Gear tabs shows the weapon's damage range against small and large targets, swing delay, defence ratio, and what the worn set contributes on each defensive axis; picking the tab that is already open folds the pane away again. Defence ratio and the damage ranges are real totals and their formula moved into the shared calculation header so the server's copy can adopt it rather than drift from it. The absorption and resistance rows are not totals and the pane says so on screen: those aggregates exist only on the server and are not on the wire, and putting them there is a Compatibility bump that has not been spent.
- **The palette stopped having two words for one colour.** The theme's "caption" and "disabled" are now aliases of the game colours that were re-tuned for these dark panels in the first place, rather than a second near-identical pair free to drift; six semantic colours with no consumer, an unused equipment-cell primitive and two unread metrics were removed rather than left looking like supported vocabulary. Sixty-five cursor reads left behind by the button conversion went with them — dead stores that would have warned on the Linux build.
- Verified: Windows Debug green for both targets, and Windows Release green for the client, which is what was deployed. **Not verified on screen** — the pane's layout arithmetic and the converted dialogs have only been checked by reading, not by looking.

# One database for the whole world, and every item row remembers which item it is

Issue #77 (epic #74, Item Provenance Ledger phase 1.2), implementing ADR 0004 and the Serial half of ADR 0003. The account store was one SQLite file per account — a layout inherited from flat-file thinking — and item rows had no Serial, so #75's identity died at the first save. This is one schema epoch that fixes both, because persistence should churn once. Server 0.18.0 → **0.19.0**; Client stays 0.9.1 and **Compatibility stays 0.9.0**, since Serials still never touch the wire.

- **The decisive reason for one file is atomicity, not tidiness.** SQLite transactions across ATTACHed databases are **not atomic in WAL mode**, and WAL is mandatory under ADR 0003. So an Exchange between two players was permanently two commits with a window between them: a crash in that window duplicates or destroys an item, which is the exact exploit class this whole effort exists to close. No amount of careful code fixes that under the per-file layout. `accounts/*.db` becomes one `game.db`, which is what makes #82's atomic trade commit possible at all.
- **Uniqueness stopped being a directory scan and became a constraint — and the collation is the part that had to be right.** `character_name` was already `PRIMARY KEY` per file, so global uniqueness comes free in one database. What did *not* come free is case-insensitivity: the scan it replaced compared `COLLATE NOCASE`, so a plain `PRIMARY KEY` would have quietly started allowing `probeone` beside `ProbeOne` — a name-impersonation hole introduced as a side effect of a storage change. Every name column is declared `COLLATE NOCASE`, including on the child tables, where it is also what keeps `WHERE character_name = ? COLLATE NOCASE` an index seek instead of a scan across every character's inventory.
- **`block_list` was the one table whose owner was its filename.** Its primary key was `blocked_account_name` with nothing saying whose list it was, because the file answered that. In one database it needs an `owner_account_name` column, and its delete-then-insert save needs a `WHERE` — unscoped, one player logging out would clear every player's block list, silently. Both halves are asserted separately, because the read and the write fail differently.
- **The mass-save sweep is one transaction, and nesting is SAVEPOINTs rather than a depth counter over BEGIN/COMMIT.** `SaveCharacterSnapshot` runs its own transaction and `save_all_players` now wraps the whole sweep in one — but with plain nesting, one character failing to save would `ROLLBACK` the enclosing transaction and take *everyone's* snapshot with it, which is strictly worse than the per-file layout it replaced. Inner scopes are savepoints, so a failed character is undone alone and the sweep still commits. That is the behaviour the old layout had by accident, kept here on purpose.
- **Four directory walks became four queries.** `CharacterNameExistsGlobally`, `AccountNameExists`, `ResolveCharacterToAccount` and `CountAccountStats` each opened and queried *every file* in `accounts/` — O(accounts) file opens to answer what an index answers in one seek, two of them on the login path. `CountAccountStats`'s over-limit report also now names the account as stored rather than the lowercased filename it had to use before. `AccountDbExists` is gone: "is there a file named after it" was a weaker question than it looked, since the file could exist with no `accounts` row in it — an interrupted account creation left exactly that.
- **The connection is held for the process, with a statement cache, and the two RAII scopes decide by identity.** `stmt_scope` and `txn_scope` take a raw `sqlite3*` and use the cache and the nesting transaction *if that handle is the live Game DB*, falling back to prepare/finalize and plain BEGIN on any other — which is what let every existing call site opt in without a signature change, and what lets `gamedbcheck` drive a scratch file. The scopes also close a real hazard the old manual `sqlite3_finalize` had: a SELECT abandoned after its first row keeps a read transaction open, and under WAL that is enough to make a later COMMIT fail. Scope exit is a place a finalize cannot be forgotten — and on several error paths it had been.
- **Both pre-v8 refusals stop the boot with a sentence, because there is no migration (D6).** A surviving `accounts/` directory and a `schema_version` below 8 are each a world from before this change, and the wrong answer to both is to boot a fresh empty `game.db` next to it and let an operator discover the wipe by finding every character gone. Both are asserted in *both* directions — a detector that always fires would refuse every boot, and only the never-fires half of that is visible in ordinary testing.
- **Serials ride the same epoch: `character_items`, `character_bank_items`, and the Trading Post's `listing_items` / `offer_items` all gain a `serial` column.** Escrow matters as much as inventory: a Listing is a custody transfer, not a destruction and re-creation, so an item that lost its Serial in escrow would read to Reconciliation as one item vanishing and an unrelated one appearing. `0` is written and read back as `0` for Counted (stackable) rows — a load path that helpfully filled it in would mint a Serial for a stack on every login. Two indexes on the Serial columns land now rather than later, because adding an index afterwards is a schema bump and a schema bump is a world wipe.
- **Ground items carry no Serial through persistence, and that clause of the plan is vacuous rather than skipped.** Ground items live in map tiles in RAM (`Map::set_item`) and have never been persisted at all, so there is no ground-item state for a Serial to survive in. Their lifecycle instrumentation is #79's, in the ledger, not here.
- Evidence: the new `gamedbcheck` harness (`Server --gamedbcheck`) proves the P1.2 contract headlessly — **23/23 on both platforms**, covering the live connection's WAL / `synchronous=NORMAL` / foreign-key posture, both refusals in both directions, global and case-insensitive name uniqueness, the Serial round trip through **both** the vector insert path *and* `SaveCharacterSnapshot`, Counted rows staying at 0, cascade delete, block-list scoping on read and write, statement-cache reuse, and nested rollback isolation. It writes to a scratch database and its own probe accounts directory, and deletes both — the cleanup is itself a check. Verified to go red twice: breaking the name collation, the block-list scoping and the nested rollback turned 4 of 23 red, and separately dropping the snapshot's Serial bind turned `snapshot_serial_round_trip` red while the vector-path check stayed green, which is what proves the two are genuinely different code paths. Windows Server Debug green (only the pre-existing `LNK4098` from the release-built bundled `sqlite3.lib`). Linux green on a **full** server-subset sync to `~/hb38-ci` — this cycle adds four files and `SERVER_SOURCES` is an explicit list, so the build log naming `GameDatabase.cpp.o` and `CmdGameDbCheck.cpp.o` is the proof they were not silently omitted. On the same `gamedata.db` (md5 `888948e1…`) all four provers are byte-identical across platforms: `GAMEDBCHECK` **`d5148aae…`**, `SERIALCHECK` **`9442eea8…`**, `LEDGERCHECK` **`7092d493…`**, and `DROPODDS` **`f8e51b4e…`** — the last being the value #91, #102, #90, #67, #75 and #76 all recorded, so the drop pipeline is provably unmoved. Both platforms produce an identical `game.db`: WAL, schema 8, 11 tables, 3 indexes.
- Worth knowing: `tradingpost.db` bumps 2 → 3 for its Serial columns, so it is wiped alongside the account files. `scalar` / `text_scalar` were about to exist in two provers, so they moved into the shared `CheckTally` scaffold as `probe_scalar` / `probe_text` — `serialcheck` and `ledgercheck`'s recorded hashes are unchanged, which is how that extraction was verified as a pure move. `OpenAccountDatabaseIfExists` is now `AccountDatabaseIfExists`, since it no longer opens anything. The `wmain.cpp` / `Wmain.cpp` case collision on the Linux sync bit again exactly as recorded and needed the same `mv -f`.

# An item's Serial now outlives the process that minted it

Issue #76 (epic #74, Item Provenance Ledger phase 2.1). #75 gave items identity but only in RAM: every restart restarted the sequence, so a Serial meant nothing across a reboot and there was nowhere to write an item's history. This builds `itemledger.db` — the append-only store the biographies live in — and makes the Serial sequence survive a restart. Server 0.17.0 → **0.18.0**; Client stays 0.9.1 and **Compatibility stays 0.9.0**, because Serials still never touch the wire.

- **The store is a passive audit trail, and the code shape enforces it.** Every recorder returns `void` and does nothing but append to a RAM buffer; only `flush()` can fail, and it fails to a log rather than to the caller. That is not politeness — D3 says the in-RAM world stays authoritative, so a ledger write must never be able to fail the game action that caused it. The whole buffer then goes to disk in one transaction on a cadence, which means a crash can lose a whole flush window but never half of one.
- **Recovery takes `max(meta.serial_high_water, MAX(item_instances.serial))`, because the two sources fail in opposite directions.** The durable mark can be stale — a crash lost the flush that would have advanced it. The instance table can be behind — those same birth rows were in that lost flush. Either one alone can undercut the true high-water, and handing out a Serial a stored item already holds is the single failure Reconciliation cannot tell apart from a real dupe. The higher of them is the only value neither hole can undercut. `ledgercheck` stages both states on a scratch database and proves each direction.
- **A failed flush keeps its buffer instead of dropping it.** An audit log that discards what it could not write has exactly the gap it exists to prevent, so the rows are held and the next flush retries them. That created a second problem worth naming: the held rows keep the size trigger armed, so a stuck write would have replayed the entire batch on every 20 ms tick, each attempt forcing a synchronous error-log write. The size trigger is disarmed while a flush is failing and the interval carries the retry — the promise is kept without the busy loop.
- **Boot writes a run-boundary event, and it says whether the previous run ended cleanly.** A plain "the server restarted here" marker does not answer the forensic question; what a query needs to know is whether the events before it are all there. A `clean_shutdown` flag in `meta` is written the moment the store opens and cleared on close, so a boundary reading `crash` means the tail of that run may be missing and one reading `clean` means nothing is. The marker uses serial 0, which is already the "unserialed" sentinel.
- **WAL from birth is about readers, not write throughput.** Under WAL an external process can query the live file while the server writes, which is what lets the reconciliation and analytics tooling of phase 4 run against a running world instead of a stopped one. The mode is read back and verified after `open()` rather than assumed — a file that silently stayed in rollback-journal mode would look fine until an external reader blocked the server.
- **The event-type numbering is frozen now and enforced by the compiler.** `item_events.event_type` passes `ItemLogAction` values straight through (1..99) so the dual sink in #78 needs no translation table, with ledger-only transitions from 100 up. Stored values are permanent world fact once real players exist, so a collision would make one number mean two things with no way to disambiguate afterwards. `ItemLogAction` gained a `max_action` marker and the ledger `static_assert`s against it: growing the taxonomy into the ledger band is now a build error rather than a review miss.
- **The flush cadence is data.** `ledger_flush_ms` and `ledger_flush_events` live in `server_config.json` and move live on `reload config`; deliberately not folded into `autosave_ms`, because autosave is per-character and staggered across ten minutes while the ledger buffer is one global batch whose loss is measured from the last flush. The store's own defaults are zero — "explicit flushes only" — so the numbers have exactly one home and cannot drift; every boot logs the cadence it actually resolved, which is how a config that lost the keys gets noticed as a log line instead of as events that never reached disk.
- **`ledgercheck` is the prover, and it works on a scratch database.** Most of what matters here is only observable across a close/reopen boundary, which the live store cannot demonstrate without stopping the server — so the command creates its own file, drives it through a full restart including a simulated crash and a simulated lost flush, and deletes it. Deleting rows out of an append-only audit log to clean up after a test would have been a worse habit than the coverage it bought. 18 checks, byte-identical on Windows and Linux; disabling the buffer-retention and the recovery-max rule turns 3 of them red, so it is not decorative.
- Side effects worth knowing: `serialcheck` and `ledgercheck` now share one scaffold, because the machine-readable format is what the Linux gate byte-compares and a per-prover copy lets a format tweak desynchronise the other's baseline (`serialcheck`'s recorded hash is unchanged, which is how that refactor was verified). The three per-table insert loops are one parameterized batch writer rather than the same twenty lines in triplicate. `early_exit` in `wmain.cpp` now flushes the ledger, because the headless one-shots mint Serials and reach the process exit without going through `quit()`.

# Items are born in one place now, and they are born with a name

Issue #75 (epic #74, Item Provenance Ledger phase 1.1), the first cycle of ADR 0003. An item had no identity: two +7 swords were indistinguishable to the server, which is why dupe detection was statistical inference and "I lent it to him" was unanswerable. This gives every Instanced item a permanent Serial at creation and makes one function the only way an item can come into existence. Server 0.16.0 → **0.17.0**; Client stays 0.9.1 and **Compatibility stays 0.9.0** — Serials never touch the wire, which is the whole point of D1 and the reason the Item Tiers one-bump law is untouched.

- **The Serial had to go on `CItem` and not in `CItem::m_instance`, and that placement is the most load-bearing decision here.** `m_instance` is the POD that item-carrying packets embed verbatim (`Item.h`: "packets embed the same struct"), so a Serial inside it would have been handed to every client and silently broken never-on-the-wire — the property that stops a tampered client from even observing the tracking. It sits directly on `CItem` instead, which also means Serials cost no wire bytes and no Compatibility bump. `CItem` is shared, so the client carries an unused field that stays 0; that is intended.
- **Instanced iff non-stackable, so gold and potions mint nothing.** Stack merge and split dissolve identity, so a Serial on a stackable would be a fact the ledger could never reconcile against anything. Counted items get no origin either: `origin_type` is an `item_instances` column, and stackables get flow rows keyed by event instead, so the venue belongs on the event rather than the item. Nine creation sites pass `none` for exactly this reason.
- **All 45 `new CItem` sites across 16 files now funnel through five named entry points, and the split between them is semantic, not mechanical.** `create_item(id|name, origin)` for an item entering the world; `restore_item(id, serial)` for rehydrating one that already exists; `transform_item(new_id, from)` for an in-place evolution; `create_template()` for the item-config catalog; `create_snapshot(source)` for the throwaway copy a log line needs. A regex could not have made these calls — which is why this was 45 hand-classified edits rather than a bulk script.
- **The three classifications that would have quietly corrupted the ledger if read wrong.** *Restore is not birth*: character inventory load, Warehouse load and Trading Post escrow rehydration carry the stored Serial, because minting there would renumber every item in the world on every restart. *Transform is not birth*: the majestic evolution chain and the hero-cape upgrade delete an item and rebuild it in place, so `transform_item` carries the Serial and origin across — a fresh one would split one physical item's Biography into two instances that never met, and burn an allocator value on a phantom. *A log snapshot is not an item*: the four `item_acopy`/`item_bcopy` allocations in the Exchange path exist for one `item_log` line and are freed immediately, so they share the source's Serial rather than getting one.
- **`restore_item` mints when the stored Serial is 0, and lifts the allocator when it is not.** Until #77 adds the column every load arrives at 0, and an Instanced item must never sit in the world unserialed; the per-restart renumbering that implies is exactly what D6 wipe-freedom exists to permit. The lift matters more than it looks: without `resume_from`, a fresh in-RAM counter would re-issue a Serial that a loaded item already holds — one Serial in two inventories, the precise anomaly Reconciliation is being built to catch. `serialcheck` asserts both directions.
- **The coverage law is enforced by a script, not by reviewers remembering.** ADR 0003 says a raw `new CItem` in game code "becomes a review defect"; `Scripts/check_item_factory.py` makes that mechanical, failing on any allocation outside the factory and pinning the factory's own count at 6 so one cannot be parked inside it either. It was self-tested in both directions — a planted violation is caught, and removing it goes green.
- **Four pre-existing defects fell out of the funnel rather than being hunted.** A **use-after-free** in `StatusEffectManager.cpp` (crop harvest: `delete item` on init failure, then `item` used in both branches below). A **leak on every failed craft** in `CraftingManager.cpp`, where a `CItem` was allocated, never used and never freed. Two paths that **destroyed a player's item before checking whether its replacement could be built** — the majestic transform left a blank item in the slot, and the hero-cape upgrade spent 50 contribution and 50 EK first; both now build the replacement before anything is spent or deleted, so a missing config row costs nothing. Also removed: a throwaway `CItem` allocated purely to measure gold's weight in the sell path, which under the ledger would have read as an item being created — the config row answers the same question.
- **Origin is a taxonomy derived from the call sites, not invented.** 16 venues, one per real creation path (`npc_drop`, `shop_buy`, `craft`, `quest`, `fishing`, `mining`, `harvest`, `lottery`, `war_reward`, `hero_reward`, `dark_claim`, `angel_claim`, `magic`, `event_reward`, `gm_mint`, `restored`). A 17th, `level_reward`, was written and then deleted once the conversion proved every level-up grant is gold and therefore Counted — an enum value no code can reach is a lie about what the system does.
- Evidence: the new `serialcheck` harness (`Server --serialcheck [instanced_id] [counted_id]`) proves the contract headlessly in the role `mintcheck` plays for the legality gate — **9/9 checks pass on both platforms**, covering mint, uniqueness, origin recording, Counted staying unserialed, restore carrying, the high-water lift, restore-with-0 minting, and transform carrying both Serial and origin. Its machine lines deliberately contain **no absolute Serial numbers**, since the allocator's position depends on what the process did earlier and the Linux gate is a byte comparison. It was verified to go red: disabling the mint turned 4 of the 9 red rather than passing anyway. `Scripts/check_item_factory.py` green. Windows Server Debug green, **0 warnings, 0 errors**. Linux green on a **full** server-subset sync to `~/hb38-ci` — this cycle adds three files and `SERVER_SOURCES` is an explicit list, so a diff-only sync would have produced a green binary with `CmdSerialCheck.cpp` silently absent; the build log naming `CmdSerialCheck.cpp.o` is the proof it was not. Both binaries on the same `gamedata.db` (md5 `2b81d6be…`): the 10 machine `SERIALCHECK` lines hash **`9442eea8…`** on Windows and Linux alike, and the 38 machine `DROPODDS` lines hash **`f8e51b4e…`** — the same value #91, #102, #90 and #67 recorded, so the drop pipeline is provably unmoved by a refactor that touched every item-creation site inside it.
- Worth knowing: `copy_item_contents` is now private with `create_snapshot` as its only sanctioned caller, because a copy that outlives the log line it was made for is a Serial held by two objects. Its declaration also had its parameter names **backwards** — the header said `(original, copy)` where the definition means `(copy, original)` — which is fixed. `create_snapshot` now initialises by `m_id_num` instead of `m_name`, replacing a normalised scan of the whole item config with a direct index, on a path that runs per item on every Exchange. `ItemProvenance.h` is header-only on purpose: no new `.cpp` means no `CMakeLists.txt` churn for the allocator itself, and `serial_allocator::resume_from()` is the seam #76 attaches the durable high-water mark to, so that ticket is wiring rather than another sweep of the call sites. # The boss scatter had a floor under it, and we had been rolling without one

Issue #89 (epic #36), unblocked by #91's Bag of Gold. Our three scatter bosses dropped roughly half what the original gave — Wyvern 3.80 items a kill against 6.90, Abaddon 8.60 against 13.77 — and the cause was the mechanism, not the numbers. Server 0.15.0 → **0.16.0**; Client stays 0.9.1 and Compatibility 0.9.0, since no wire message and no named-unique roster entry changed.

- **The original's yield floor is a fallback item, not a probability.** `bGetMultipleItemNamesWhenDeleteNpc` (`repos/HB382_CENTUU/HGServer/Game.cpp:47119`, byte-identical to `repos/HelbreathServer/HGServer/Game.cpp:48051`) loops `iMax` times and splits the loop with `if (i > iMin) iProb = iProbability`: the first `iMin+1` rolls run at full rarity and end with `if (iItemID == 0 && iProb == 100) iItemID = 90;`, so **an empty head roll pays out Gold instead of nothing**. That single line is why a Wyvern always dropped at least six items. The remaining rolls multiply every rarity bound by `fProb` 5.0 — the same factor in all three of its blocks, so one integer divisor reproduces the whole tail. Effective yield is `head + tail/5`: 6 + 9/5 for the Wyverns, 13 + 7/5 for Abaddon. Our port instead rolled a flat 15/15/20 times against a table with a large "nothing" remainder, which is where the entire shortfall came from.
- **So the guarantee is modelled as a fallback, and deliberately not as a guaranteed row.** `drop_tables` gains `guaranteed_rolls`, `guarantee_item_id` and `tail_rarity_divisor`; the head's remainder substitutes the guarantee item. Making Gold a real row instead would be wrong twice: it would also become winnable on the *tail* rolls, where the original can yield nothing, and it would overshoot the mean by 0.9 items a kill on a Wyvern. The guarantee item carries a **0-ppb row** for its count spec alone — so how much gold a pile holds is authored next to the gold — and the validator ties the two together in both directions, with `drop_entries_readable` NULLIFing the divisor so `1e9/0` never happens.
- **Owner override: the rosters come from the Olympia wiki, not the original's blocks.** <https://www.helbreath.net/wiki/Monsters_and_drops> for Ice Wyvern / Fire Wyvern / The Abaddon, its Uncommon and Rare columns, mapped onto our ids and filtered to what we carry. That source also settled two open questions on its own: its Ice Wyvern lists **all seven live items of the original's mislabelled `case 69` block**, confirming the owner's decision to repair it (the archive labels the Wyvern rare block `case 69`, but 69 is Devlin and Wyvern is 66, so it is unreachable dead code in both archives); and its Fire Wyvern carries the whole 9-case rare block that **our own `Scripts/sim_original_scatter.py` had silently omitted**, which means every Fire-Wyvern composition figure that script has ever printed understated the roster.
- **The rate rule is `max(the original's rate for that boss, the Olympia tier anchor, a floor)`, so nothing tightens by accident.** Anchors per head roll are 1 in 48 for Uncommon (the original's own common-block single-case rate) and 1 in 240 for Rare (Abaddon's rare block), and the floor is the Rare anchor. The floor is load-bearing: without it, ids Olympia does not list — Necklace of Xelima and Mass Fire Strike Manual on Fire-Wyvern, Necklace of Stone Golem on Abaddon — would have tightened by **three orders of magnitude** against the shipped data purely as a side effect of swapping rosters. Those two anchors are the balance knobs, one line each in `Scripts/derive_scatter_rosters.py`.
- **Against the shipped data every row either tightens or is new, which is the opposite of what the ticket assumed.** Today's boss tables held *only* the rare/unique block, spread across all 15 or 20 rolls, so uniques were near-guaranteed: Necklace of Ice Protection at 1.19 a kill, Excalibur 1 in 7 kills from Abaddon. #89 adds the entire common block plus Gold — items these bosses could not drop at all — and tightens the uniques 3× to 36×. The only removal anywhere is **861 Berserk Magic Wand (MS.20)** from the two Wyvern tables, and it still drops from Demon, Ettin, Centaurus and Giant-Lizard, so no content is lost.
- **Scatter gold has its own amount, and it is 30× what we were paying.** The original hardcodes `iDice(10, 15000)` — ten rolls of 1..15000, so ~75,005 a pile, tightly clustered — and pointedly does **not** use the monster's gold dice, which is what stage 1 uses (`:47334`) and what our engine was substituting for every gold row. A Wyvern was paying ~2,500 a pile. `drop_entries` gains `count_throws` and the rule "an authored count beats the monster's dice"; all 22 pre-existing gold rows author `0,0` and are untouched. A single uniform roll over 10..150,000 would have had the right mean and three times the spread, so the throws matter.
- **The original's comment lies about item 738, and the id wins — #71's lesson and #90's, for the third time.** Both Wyvern blocks drop `738`, which the drop code labels "BerserkWand(MS.20)"; the original's own `Item.cfg` says 738 is `DarkMageMagicWand` and **861** is the Berserk wand. Our port had followed the comment. Olympia lists neither wand, so both readings were available and the id decided it.
- **Five ids the original's own blocks reference never existed anywhere.** 936 Merien Hat, 937 Merien Helm (two of Abaddon's six jackpot slots), 947 Dragon Staff (MS.40), 942 Ice Hammer and 943 Ice Axe are all above the original's roster ceiling of 890, so `_bInitItemAttr` failed there exactly as it would here and those slots dropped nothing. Owner decision: no rows. The ticket's own "Merien Hat / Merien Helm ~1 in 330 kills" figures were phantom.

Per-kill gold still lands at 182k / 156k / 328k against the original's 218k / 218k / 460k. Yields land on target — Wyvern **7.07** a kill over a **6–13** range, Fire Wyvern **7.18** over 6–14, Abaddon **13.93** over **13–20** — against targets of 6.90 / 6.90 / 13.77 and ranges 6–13 / 6–13 / 13–19.

Our stage-1 tables do give them gear. That is the owner's deliberate design, not a deviation to fix, and #89 does not touch stage 1.

Windows Server Debug green, 0 errors. Linux green on a **full** server-subset sync to `~/hb38-ci` (`SERVER_SOURCES` is an explicit list and this cycle adds a file). # Reputation can go up again, and it pays out where the original paid out

Issue #88 (epic #36). Reputation was a one-way ratchet downward — combat could subtract from it and nothing could ever add — and the drop modifier it feeds had been wired to the wrong outcome before #73 deleted it outright. Both halves are closed: the player-to-player vote gets its two entry points back, and the modifier returns as a fifth layer of the generosity stack. Server-only; **no wire change** (the packets and the client handlers were already there). Server 0.12.0 → **0.13.0**.

- **The vote handler was never missing — nothing called it.** The ticket reported `RATINGPLAYER` as absent from the codebase. In fact `CGame::set_player_reputation` was a faithful port sitting complete and unreachable: level-40 gate, PK-count gate, town-affiliation gate, self-vote block, ±500 clamp, 20-minute cooldown, notifications to both parties. `Notify::RatingPlayer` and `Notify::CannotRating` were already on the wire and the client already handled both. `m_time_left_rating` was already ticking down at 1 Hz and already persisting. The original reached this code from a `memcmp` chain on `/rep+ ` and `/rep- `; our port replaced that chain with `GameChatCommandManager` and did not carry the two commands across. So the whole live defect was two unregistered commands — and the fix is `GameCmdRep.h/.cpp`, two classes at permission level 0, because what gates a vote is the voter's own level and cooldown, not an admin rank.
- **The handler's argument parsing had to change or every vote would have silently done nothing.** It took the *second* `strtok` token, correct when the original handed it the whole `"/rep+ Name"` string and wrong now that the dispatcher strips the command word first — it would have read past the name and found nothing. It takes the bare name, keeping the same first-word truncation and the same separator set, so a name arriving with a trailing newline still resolves.
- **The rating modifier comes back as a per-player layer, which is where ADR 0005 said it belonged.** #73 deleted it along with the flat 5% stage-2 gate it had been attached to, so the defect the ticket describes — criminals receiving up to 3× the second-drop rate — no longer existed by the time this was worked. What was left was the other direction: reputation affected drops not at all, and in the original good reputation was a bonus. The stack becomes `drop_chance_ppb × (global × stage × category × grade × rep)`. Unlike the four stored multipliers, `rep` is computed per kill from the killer's rating.
- **Scoped by category, not by stage, and that follows from where the items are.** It applies to `gear` and `unique` rows and never to gold or consumables, so an outcast is slowed but never starved — their coin and potions drop at the ordinary rate. Scoping by category rather than by slot is what lets one rule cover both: tier-scope gear is stage-1 only, while the named uniques live in stage-2 tables, so a stage-scoped term could only ever have reached one of the two things a player actually farms for.
- **The curve is the original's, read as a factor instead of a branch threshold.** The original computed `dTmp1 = rating × m_cRepDropModifier` clamped to ±1000, then split consumable-vs-equipment at `9000 − dTmp1` out of 10000 — which on the equipment side is exactly `1.0 + dTmp1/1000`, a 0.0…2.0 factor sitting at 1.0 for a neutral player. Verified identical in both archives (`repos/HB382_CENTUU/HGServer/Game.cpp:47347`, `repos/HelbreathServer/HGServer/Game.cpp:48279`). The clamp is on the product rather than the rating, which is why it saturates at rating ±200 while rating itself runs to ±500.
- **One deliberate deviation: the floor.** The original let the equipment side reach exactly zero, so a player at −200 or worse received no equipment at all, permanently. Ours floors the factor at 0.25 — a quarter rate rather than none — because a penalty other players inflict by vote should not be able to lock someone out of the game's core reward loop. Owner decision. Everything else about the curve is the original's.
- **All three knobs are data, and one of them is an off switch.** `drop_multipliers` gains a `reputation` scope with `modifier` (5.0), `floor` (0.25) and `cap` (2.0), seeded on boot with `INSERT OR IGNORE` so an operator's tuning survives — seeded rather than left implicit precisely because these are the only rows in that table whose neutral value is not 1.0, and an invisible knob is one nobody turns. `modifier = 0` disables the layer outright, the same escape hatch the original's 0-floored config token had. All three reload live with `reload tiers`.
- **The boot validator refuses a window that excludes 1.0.** A `floor` above 1.0 or a `cap` below it would silently scale a *neutral* player, which would make every published drop figure in the project wrong rather than just mis-tuning one lever. Both branches were negative-tested to a refused boot, as was the disable path. A negative-modifier check was written and then removed on review: the loader already rejects a negative value on any multiplier row before it reaches the struct, so it was a dead branch.
- **`dropodds` learned whose kill it is pricing.** `dropodds [grade] [rating <n>]` and `dropodds npc <id|name> [rating <n>]`; with no argument it prices a neutral player, which is what every figure this project has published has always meant. The rating and its resolved factor ride the machine-readable `MODE` line so two runs can be diffed. The report resolves through the same `resolve_drop_chances` the roller calls, so the two still cannot disagree — the parameter is deliberately not defaulted on that function, so each of the three call sites has to state whose reputation it means rather than inherit one.
- Evidence: rating 0 leaves **every** figure byte-identical to #73's — grade 2 reads 35% / 14% / 1.400%, grade 5 gear 1.775% — which is the invariant that matters, since it means nothing changes for anyone until players start voting. At rating +500 gear is exactly 2.00× at all five grades and at −500 exactly 0.25×, with tiers scaling proportionally and gold pinned at 0.21 in every case. Verified in **both** item-system modes: legacy and tiered agree byte-for-byte on the gear, any-item and anything columns, with only the tier-split columns zeroing out — which is what "shared pipeline code, not strategy policy" has to look like. Windows `-Target Server` Debug green, 0 errors and 0 warnings. Linux green on a full server-subset sync to `~/hb38-ci` — a full sync, not a diff, because this cycle adds files and `SERVER_SOURCES` is an explicit list; `GameCmdRep.cpp.o` was confirmed absent before and compiled after. 0 GCC warnings on every recompiled unit. Both binaries against the same `gamedata.db`: 114 machine-readable `DROPODDS` lines across three ratings, **byte-identical**, sha256 `8e8112a6…`.
- Worth knowing before tuning this: the `unique` category is `is_special_item`, which covers the three stones and four Ancient Pieces sitting in every stage-1 table at 1.4–2.3% each — not just the rare named uniques. On the 49 configs using the shared boilerplate table those rows are the *entire* drop, so a maximally well-regarded player sees them at 25.2% rather than 12.6%. That is the choice working as specified, but it is a wider blast radius than "chase items", and ADR 0005 already flags those rows as misplaced stage-1 content for content curation (#91) to resolve.

# Item Tiers — a drop-table row is now an absolute rarity, not a weight

Issue #73 (epic #36), implementing [ADR 0005](docs/adr/0005-absolute-drop-chances.md) and spec §8 Amendment A1. Every `drop_entries` row stops being a weight relative to whatever else happens to share its table and becomes an absolute per-kill chance for that item from that monster. Stage 1 and stage 2 split into separate tables driven by one identical engine. **This change reproduces every current per-kill rate exactly** — its whole value is that it changed nothing. Server-only; no wire change. gamedata.db schema 9 → **10**. Server 0.11.5 → **0.12.0**.

- **The old numbers did not mean anything, and the shipped data proved it twice.** Sword of Medusa carried weight `1` on both the zombie and the snake and came out 1 in 2,000 from one and 1 in 433,000 from the other, because the snake's table also holds butcher parts that crowd the uniques down. Adding a common item to a table silently made every unique in it 200× rarer. In the other direction, Plate Mail (M) carried weight `50` in all thirteen tables it appears in, so an Ice Golem and a Dragon dropped it within 8% of each other — not because anyone tuned it flat, but because nothing could express otherwise. Under absolute rarity, adding or removing a row cannot change any other row's odds.
- **The column is `drop_chance_ppb`, parts per billion, even though rarity is authored and read as "1 in N".** Precision is not what decided it: an integer `1 in N` cannot express 30% (it rounds to `N = 3`, or 33.33%, an 11% jump on the gold row of 48 monsters), but a REAL `1 in N` would have been accurate enough. Two rules settle it instead. A guaranteed table's rows must sum to **exactly** 1.0, which is an integer equality no float tolerance can carry; and the Windows/Linux byte-identical `dropodds` gate cannot survive float accumulation order differing between compilers. Readability moved to presentation: a `drop_entries_readable` view exposes `1000000000.0 / drop_chance_ppb AS one_in` beside the raw rows, and the report prints "1 in N".
- **Four generosity multipliers, and they multiply.** `effective_ppb = drop_chance_ppb × (global × stage × category × grade)` — larger ppb is more likely, the opposite direction from the "1 in N" form the ADR first proposed. All four default to 1.0, live in `gamedata.db`, and move live with `reload tiers`; no restart-only term is left anywhere in the chain. They scale row rarity only, so they shrink a table's "nothing" remainder and **never** touch `roll_count`: turning stage 2 up cannot make Abaddon scatter more items. On a table whose rows already sum to 1.0 a multiplier is a deliberate no-op, and the boot validator names every such table so that is visible rather than a surprise.
- **One engine; "stage" is only which slot a monster references.** `npc_configs` carries `stage1_table_id` and `stage2_table_id`, `drop_entries` loses its stage discriminator, and every behaviour that used to belong to the second drop became an ordinary table property available to either slot: `guaranteed_secondary` is now "rows sum to exactly 1.0", `scatter_count` is `roll_count_min`/`roll_count_max` plus `placement`, and `delay` chooses death or corpse decay. Nothing in the roll, the rate model, the multipliers or the validator branches on which slot a table came from — a stage-1 table set to scatter/corpse-decay behaves identically to a stage-2 one. The only asymmetry left is not part of the calculation: §8 keeps stage 2 out of the tier roll, which now rides on the queued drop rather than being re-derived at placement time.
- **The gold preempt, the flat gates and the `server_config.json` drop rates are gone.** `base_gold_drop_chance`, `base_secondary_drop_chance`, `loot_grades.first_drop_chance`, `drop_rates.primary`, `drop_rates.gold` and `drop_rates.secondary` all retire; gold is an ordinary row competing on its own chance, counted from the monster's gold dice exactly as before. The reputation modifier retires with the 5% gate it lived on, which incidentally resolves #88's inversion — a player at rating 100 or above could get no second drop at all.
- **98 stage-1 tables collapsed to 23 definitions**, 13 of them shared and 10 monster-specific, with the shared ones named `s1_<monster>_x<N>` so editing one says how many monsters it moves. Stage 2 went 37 → 36. Rows went 1,902 → 867 with nothing lost: the duplication was the bundling's fault, since a monster wanting the shared potion block plus its own uniques had to copy the whole block.
- **The roll needed a real random source.** `CGame::dice` is `rand() % range`, and MSVC's `RAND_MAX` of 32767 cannot reach past the first 0.0033% of a billion — every kill would have taken the first row. The drop roll uses `<random>`, the same reason and the same precedent as `tiered_roll_strategy`.
- Evidence: `Scripts/migrate_drop_chances.py` converts with `--dry-run`, `--verify` and a full report. Across all 1,932 priced rows the worst deviation is **0.0198%** and no row moves more than 0.1%; that residual is a one-time quantisation of 2004-era weights into ppb, not an ongoing tax. The pass/fail gate holds: `dropodds` per-grade odds are **identical to eight decimals** on all five grades, before and after. Windows `-Target All` Debug green, 0 errors and 0 compiler warnings. Linux server green on a full-sync `~/hb38-ci` tree with 0 GCC warnings — a full subset sync, since this cycle adds a file and `SERVER_SOURCES` is an explicit list, and `DropModel.cpp.o` was verified to actually compile. Both binaries ran against the same `gamedata.db`: the 38 machine-readable `DROPODDS` lines are **byte-identical**, sha256 `77e79f31…` — which is the property the ppb encoding was chosen for.
- **`dropodds` stopped multiplying a chain and started reading the data.** It prints the generosity stack, then per-grade absolute odds, and gains `dropodds npc <id|name>` — every row of both a monster's stages as a percentage and as "1 in N", with the leftover "nothing" and, for a scatter table, the expected item count. It resolves through the same `resolve_drop_chances` the roll calls, so the report and the roller cannot disagree about a rate, a clamp or a multiplier. Its per-table lines are now keyed on `(table, grade)`, because the grade multiplier is part of the resolution and four stage-1 tables serve two grades each.
- **Two labelled rate changes ride on top, each verifiable on its own.** The migration report separates rows a labelled step moved on purpose from the conversion's own residual, so one can never hide inside the other.
  - **Boss stage 1 stops being a certainty** (#87, deferred into this ticket). The five bosses sat at exactly 100% of kills — 30% gold plus a 70% item roll — which left the stage-1 multiplier a permanent no-op for them and yielded a boss Legendary every 376 kills. Their non-gold stage-1 rows scale to 20%, so stage 1 totals 44% with ~2.3x of headroom restored: boss gear 1 in 56, boss Legendary 1 in 1,878. Grades 1–4 are byte-identical across this step; only grade 5 moves. Stage *2* keeps its guarantee, which was always the design — a second item on every boss kill.
  - **Legacy rates become faithful for the first time.** Ours measured 30% gold / ~6.3% consumable / ~0.65% equipment against the original's 21 / 12.6 / 1.4 / 65 — 43% richer in gold and roughly 2x stingier in both of the things players actually hunt. Grade 1–4 stage-1 tables are re-priced to the original's outcome rates, with the relative rarity of the rows inside each bucket left exactly as the migration set it. Cited against `NpcDeadItemGenerator` in both archives — `repos/HelbreathServer/HGServer/Game.cpp:48254` and `repos/HB382_CENTUU/HGServer/Game.cpp:47322` agree, and the original's own comments carry the arithmetic: `m_iPrimaryDropRate` 6500 gives 35% of kills a drop, of which 60% is gold (35 x 60 = 21%), and the rest splits 90/10 by `m_iSecondaryDropRate` (35 x 40 x 90 = 12.6% consumable, 35 x 40 x 10 = 1.4% equipment).   - Verified per monster: an ordinary grade-2 table now reads 21.000% gold / 12.600% consumable / 1.400% gear / 65.000% nothing, exactly. Grades 2, 3 and 4 report 35% "something drops" and 14% "any item" per kill. **No monster is saturated at stage 1 any more** — the boot validator's five warnings are gone, and the only two left are the guaranteed boss *second* drops, where a multiplier no-op is intended. Windows and Linux still agree byte-for-byte on the final data, sha256 `52b22958…`; rollsmoke and mintcheck unchanged.
- Not changed, deliberately: which items live in which stage. Content curation is a separate decision from how rarity is encoded, and shipping them together would destroy the only verification gate this migration has. The scatter bosses keep today's rates — `roll_count_min = max = scatter_count` — so Abaddon still scatters 8.60 items per kill on average; the capability to express the original's guaranteed 12–20 now exists, but using it is a deliberate rate change for content curation. Scatter conversion is exact in expectation per row rather than exact in distribution, because today's first scatter roll excludes "nothing" and the rest include it, which one uniform row-set cannot express.

# Item Tiers — a forgotten NPC config field is now a build error, not a shipped default

Issue #64 (epic #36). `init_npc_attr` was a hand-written 30-assignment copy from an NPC's config row to the spawned NPC, and nothing checked it was complete: the compiler cannot report a field nobody mentioned, and `CNpc`'s default initialisers made an omission read as plausible data. The config-sourced fields now live in a struct the spawned NPC inherits, so propagation is one memberwise assignment. Server-only; no wire change, no data change, no balance change. Server 0.11.4 → **0.11.5**.

- **The failure mode is removed, not detected.** `npc_config_fields` (`NpcConfigFields.h`) holds exactly the 31 `npc_configs` columns in column order, and `CNpc` derives from it. `init_npc_attr` copies the base wholesale — `static_cast<npc_config_fields&>(*npc) = config` — so a column added to the table reaches every spawned NPC with no copy code to forget. One macro column list feeds both the `INSERT` and the `SELECT`, so those two can no longer disagree about which column is which.

Nothing in the server reads `m_attribute` off a spawned NPC today, so nothing observable changes, but it is now carried like every other field. - **A shadowed member went with it.** `CNpc` declared its own `short m_type` alongside the config's — a second field of the same name that would have silently diverged from the row it was named for. Moving the config fields into the base left exactly one.
- Evidence: Windows `-Target Server` Debug clean rebuild green, 0 errors, 0 warnings. Linux server green on a full-sync `~/hb38-ci` tree, 0 GCC warnings on every recompiled translation unit. # Item Tiers — the drop-odds report prices the gold preempt per monster

Issue #72 (epic #36), a follow-up to #66 that the #68 measurement surfaced. A gold drop skips the stage-1 item roll, and the report scaled every figure below it by the chance gold misses — but the pipeline only preempts when gold is actually *placed*, and 63 of the 111 monsters that can drop have no gold dice at all. - **The offline replica was corrected in the same shape**, since it exists to reproduce the report on a workstation and is what ADR 0005's measurement was costed against. ADR 0005's table carried the understated cell with a footnote pointing here; it now carries the corrected figure and says so.

# Item Tiers — drop odds became a number you can read

Issue #66 (epic #36). "How often does a player see tiered gear" was not a number anywhere in the system: it is the product of a hardcoded gold chance, two `server_config.json` multipliers, a per-grade `first_drop_chance`, the gear share of whichever stage-1 drop table the monster uses, and a per-grade tier weight — spread across a C++ constant, a JSON file and two database tables. The new `dropodds` console command multiplies that chain out from the running config and prints it. Server-only; Compatibility untouched, Server 0.11.1 → **0.11.2**.

- **The report is arithmetic on live config, not a second opinion.** Every term is read at the moment the command runs — `loot_grades`, `npc_configs`, the drop tables, both drop-rate multipliers, and the boot-selected roll strategy's own `first_drop_chance` — so `reload tiers`, `reload npcs` and `reload config` show up in the next report with no restart, and the mode the server is actually running is stated on the first line.
- **The gear share of each drop table is the half nobody could see, and it dominates.** A stage-1 table is mostly potions and meat; the fraction of its weight that lands on tier-eligible gear is what turns a 10% drop chance into a 0.6% chance of gear. It is now a column per table, and the per-grade rows resolve it into a per-kill probability for a drop at all, for tiered gear, and for each of the four tiers — printed as percentages and again as "1 in N kills", because that is the shape a tuning decision is actually made in.
- **Classification asks the roller instead of restating it.** `is_tier_scope_gear` — the §1 class check plus the named-unique exclusion — moved onto the roll-strategy seam, and the tiered roll, the GM mint gate, the boot validator's drop-table sweeps and this report all call it. Three more shared moves close the same gap: `base_gold_drop_chance` / `base_secondary_drop_chance` / `apply_drop_multiplier` left `EntityManager.cpp`'s statics for its header, the guard/dummy/crop exclusion became `npc_type_never_drops` (the pipeline's own switch now calls it), and `loot_grade_config::tier_weight` is now the one place that maps a tier onto its weight column, used by the roll and the report alike. A report that disagreed with the roller would be worse than no report.
- **It is a regression net as much as a tuning tool.** #63 — every monster in the game rolling as grade 2, which made Epic unreachable and Legendary impossible — took an owner playtest of roughly 500 kills to notice; it is one glance at the `npcs` column here. Any monster whose loot grade falls outside the ladder is printed as a `NOT PRICED` line rather than folded into an excluded tally, and monsters with no drop table are counted per grade, since both silently remove a monster from the economy.
- **Numbers as the shipped data actually stands** (primary ×1.00, gold ×1.00): a boss kill yields tiered gear once in 11 kills and a Legendary once in 376; elite Legendary is one in ~32,000; vermin gear is one in ~1,690, dragged down by the 14 of 69 vermin configs that have no drop table at all. The boss figures are looser than the §8 estimate written before implementation (one Legendary per ~590 kills) because the stage-1 boss tables were curated since — Abaddon's gear share is 13.6%, not the ~8% the spec assumed. Nothing was retuned in this cycle; the point is that a retune is now a calculation.
- Usage: `dropodds` for the whole picture, `dropodds <grade>` to drill into one grade's tables and list its monsters one by one. Machine-readable `DROPODDS MODE|GRADE|SPLIT|TABLE` lines ride along, and `Server --dropodds [grade]` runs it headlessly like `rollsmoke` and `mintcheck`.
- Evidence: Windows `-Target Server` Debug green, 0 errors, 0 warnings. The reported tier splits match `rollsmoke` at 200,000 rolls per grade — grade 5 reported 35/40/22/3 against an observed 34.95/40.05/22.01/2.99, grade 4 reported 60/32/7.5/0.5 against 60.10/31.93/7.45/0.52. Abaddon's 13.5939% gear share matches the figure an independent pass measured before this cycle. Legacy mode smoked by flipping `meta.item_system` and restoring it: the tier columns blank out and the tier-split table is omitted. `mintcheck` still accepts a tier-4 Sabre and still refuses item 90 and Excalibur with their own distinct reasons, so the mint-gate split survived the refactor.
- Left for the owner: the Linux server build gate, and confirming `reload tiers` reflection interactively — a piped console session is Linux-only, so on Windows the reload path is verified structurally (`reload_tier_tables` replaces `m_tier_config` wholesale, which is the accessor the report reads) rather than by running it.

# Client crash fixed — equipping into a slot whose previous item no longer existed

An access violation in `inventory_manager::unequip_slot`, reported from a live client: double-clicking an item to equip it read item id `m_item_equipment_status[equip_pos]` and dereferenced `m_item_list[that id]` with no check that the entry was still there. Client-only; Client 0.8.1 → **0.8.2**.

- **The equip-status table could name an inventory slot that had already been emptied.** `erase_item` cleared the order table, the shortcuts, the item itself and the equipped flag — but never the equip-position table, so it relied entirely on each caller having cleared the right slot first. Three of the five callers cleared the wrong one: `HandleItemDurabilityEnd`, `HandleItemReleased` and `HandleDropItemFin_EraseItem` indexed by `m_item_list[i]->m_equip_pos`, the *instance* field, which the client never populates — `init_item_list` ignores the `equip_pos` byte the packet carries, so it reads 0 (`EquipPos::None`) for every inventory item. Those three cleared slot 0 and left the real slot pointing at an item that was then erased. Dropping an equipped item and equipping a replacement into that slot is the reported path.
- **The slot question is now answered by sweeping, not by guessing.** `release_equipment_slots(item_id)` clears every equip position naming that item and marks it unequipped, so no caller has to work out which slot the item occupied. All five network handlers use it — including the two that were already correct via `cfg->m_equip_pos`, since a single spelling is worth more here than the two saved iterations — and `erase_item` calls it itself, which is what makes the invariant hold no matter what a future caller forgets.
- **`unequip_slot` no longer trusts the table it reads.** A stale entry now clears itself and returns instead of dereferencing an empty slot, which keeps the crash impossible even if some path reintroduces a stale write. The item pointer is fetched once and reused rather than re-indexing through `m_item_equipment_status` five times, and the `equip_pos >= 11` literal is now `to_int(EquipPos::LeftFinger)` — the same spelling the two dialog boxes already use for the identical angelic-stat gate.
- **The matching unchecked write is guarded too.** `equip_item` rejected only `EquipPos::None` before indexing `m_item_equipment_status[cfg->m_equip_pos]`, so a config row carrying a position outside the 15-slot table would have written past the array. It now range-checks, taking the same "this item cannot be worn" path.
- Evidence: Windows `-Target Game` Debug green, 0 errors. `git diff` reviewed — the angelic-stat branch, the release message and the ordering of the two clears are unchanged; only the indexing changed. The fix is inherently interactive to confirm: drop or destroy an equipped item, then equip a replacement into that slot.
- Not changed: `init_item_list` still leaves the instance `m_equip_pos` at 0. Nothing reads it on the client now that the three handlers don't, so populating it would only re-arm the same trap for the next reader.

# Item Tiers — damage-over-time ticks float a number over their victim

Issue #70 (epic #36). Bleed and poison each took HP every couple of seconds and said so only in a chat line, which is why a working bleed still read as nothing happening. Both now push a floating number over the victim, visible to everyone in view, colored by which effect produced it. Third and last of the three cycles riding the single Compatibility bump **0.8.0 → 0.9.0**.

- **Neither DoT had a number, so this fixes poison too.** The ticket was written about bleed, but poison has been silent in exactly the same way since long before tiers existed — it pushed `"You took -N poison damage."` into the scrolling event list and nothing else. Both route through one new message rather than bleed getting a bespoke one.
- **Two tempting reuses were both wrong, and the design is shaped by avoiding them.** `Type::Damage`/`Type::DamageMove` already carry a damage number to nearby clients, but that path locks the movement controller, cancels casting and plays the damage animation — a bleeding player would have been interrupted every second for eight seconds. `Notify::StatusText` already draws floating text, but the client hardcodes it to `m_player->m_player_object_id`, so it can only ever render over yourself and remote victims would show nothing. The new `CommonType::DotTick` instead rides the existing type-B nearby transport (`v1` = victim object id, `v2` = amount, `v3` = kind), which is position-addressed and already reaches everyone in view — no new packet struct, no new broadcast machinery, and object ids top out at 30000 so they fit its short fields as-is.
- **The number is what was actually lost, not what the tick was worth.** Both effects have paths where the full tick does not land: poison clamps at 1 HP, and a bleed whose attacker can no longer be identified clamps at 1 HP rather than killing anonymously (the 3-D credit rule). Each exit computes the real delta, and the lethal paths send *before* the kill is resolved — `client_killed_handler` and `on_entity_killed` tear the victim down, and a killing tick deserves its number the same way an ordinary killing blow gets one.
- **Player bleed moved onto the 300 ms poll, which is what makes the retuned interval real.** `tick_bleed` settles at most one tick per call, and its catch-up clause resets to `now + interval` rather than firing a backlog — so a caller polling no faster than the bleed interval silently *drops* ticks. NPC victims have always polled at 300 ms through the NPC sweep, but player victims rode `RegenManager::process_client_tick`, which runs on the 1 s `check_client_response_time` gate. At the old 2 s interval that was invisible; at the new 1 s interval a player would have landed seven ticks instead of eight. `CGame::tick_player_bleed` now polls players on the game tick, gated on the debuff being live before the call so a non-bleeding client costs one load and a branch — the same shape the NPC sweep uses. Poison stays where it was; its interval is far coarser. The constraint is now written on `tick_bleed` itself rather than being something a caller had to infer.
- **A params-table field that had been lying for as long as it existed now tells the truth.** DoT ticks need per-kind color, and the floating-text params table already declares `m_color` per row — but the sprite-font draw path ignored it and hardcoded `Yellow2x`, so the damage rows claimed `UIDmgYellow{255,255,20}` while rendering `Yellow2x{160,160,16}`. The draw now reads `params.m_color`, and every existing sprite-font row was corrected to state the color it was already rendering, so **not one pixel changes** — `LevelUp` and `enemy_kill` included, which sit on the same branch and would otherwise have visibly brightened. `magic_cast_name` draws in its own branch against a hardcoded `Red4x`; its row now says `Red4x` too. This is what lets a DoT row simply pick green or red instead of needing a special case in the renderer.
- Poison uses `PoisonText`, already this codebase's poison green (the HUD draws a poisoned HP number in it), rather than a new constant; bleed uses `Red4x`. Both are small sprite-font numbers with the same motion as an ordinary hit so they read as damage, given a slightly longer life because a tick has no attack animation drawing the eye to it.
- Evidence: Windows `-Target All` Debug green, 0 errors, 0 compiler warnings. Server boots validator-green on the tiered dev world and a Legendary Sabre carrying the bleed line mints legal via `mintcheck`. /simplify applied inline: `RegenManager.cpp`'s `StatusEffectManager.h` include went dead when the bleed tick moved out and is deleted. The visual half is inherently interactive and remains the owner's gate — a bleed tick seen from a **second** client over a remote victim is the check that matters, since that is exactly what the `Notify::StatusText` trap would have broken.

# Item Tiers — the catalog packet finishes its presentation contract

Issue #65 (epic #36). Three gaps in the replicated catalog, merged into one pass because they reshape the same packet struct, the same DDL, the same seed script and the same client read path — doing them separately meant reshaping the same five files three times. Second of three cycles riding the single Compatibility bump **0.8.0 → 0.9.0**; gamedata.db schema 8 → **9**.

- **Tooltip line placement became data.** Whether a modifier renders as its own tooltip line or merges into the damage / weight / durability line was a hardcoded switch on four modifier IDs in `category_for_modifier`. Every other presentation fact about a modifier — its label, its format, its display multiplier, its name word — already lived in the catalog and replicated; this one did not, so adding an inline modifier meant a client rebuild while every other presentation change was a database edit. `modifier_catalog.effect_placement` now carries it, the client renders whatever the row says, and the switch is gone. The four rows that are not standalone (Sharp and Ancient inline into damage, Light into weight, Strong into durability) are exactly what the old switch said, so tooltips are unchanged by this move.
- **The Bucket ordering key stopped being a stand-in, and `bucket_id` was the wrong candidate.** `tier_buckets.sort_order` existed, had no reader anywhere, and worked only because the seed happens to set `sort_order == bucket_id` for all nine buckets — reorder them in data and the column silently did nothing. The ticket allowed either replicating `sort_order` or declaring `bucket_id` ordinal and dropping the column; **`sort_order` wins**, because `bucket_id` is an identity and a foreign-key target from `modifier_catalog`, so reordering the tooltip must not mean renumbering it everywhere it is referenced. It is resolved onto each catalog row once at config load and rides the row, since buckets have no packet of their own; a row whose bucket is missing falls back to its `bucket_id`, which is exactly what the tooltip sorted on before.
- **Bands replicate, so the GM creator stops teaching by rejection.** `band_min`/`band_max` travel as two bytes per row — display units, and the widest seeded band tops out at 91, so a byte is honest rather than a squeeze; the fill clamps rather than truncates, so a future out-of-range band degrades to "the picker offers less than it could" and never to a wrapped window. The value picker now offers only values the server will accept. The legal *raw* window is the display band divided by the multiplier rounded **inward** at both ends, which is precisely the server's own legality boundary: Strong (multiplier 7, band 14..91) is raw 2..13, verified against `mintcheck` at all four boundaries — raw 2 and 13 legal, raw 1 (display 7) and 14 (display 98) rejected with the window named.
- **A freshly picked modifier now starts in-band instead of at zero.** Selecting a modifier reset its slot to value 0, which is out of band for every modifier that has a value at all, so the GM had to open the value picker before the mint could possibly be accepted. Both halves now seed at the band's low end. Setting the second half unconditionally is safe because `build_requested_attributes` already zeroes `value2` for non-pairs and `value` for zero-multiplier rows — that builder is the structural guard, and it is unchanged.
- **The two value-dropdown click cases collapsed into one.** They differed only in which half they wrote, and both needed the same new band offset; keeping them apart meant maintaining the offset twice. Options now start at the band's low end rather than at raw 1, so the selected row is an offset into the legal window and the anchor arithmetic follows it. `max_tiered_value = 20` is deleted — it was the widest raw value any seeded band reached, a constant standing in for data that now replicates.
- **Existing worlds migrate rather than needing a rebuild.** `effect_placement` is added by a `HasColumn`/`ALTER` following the `npc_configs.loot_grade` precedent from 2-A, defaulting to 0 (standalone), which is what every row but those four was already doing — so a pre-#65 world keeps rendering correctly until the seed sets the four. `reload tiers` recomputes the catalog hash and pushes to connected clients, so placement, ordering and band edits are all live data edits with no client rebuild and no restart, which is the ticket's second acceptance criterion doing real work.
- Evidence: Windows `-Target All` Debug green, 0 errors, 0 compiler warnings. Migration exercised on the real dev world — schema stamped 9, column added, all 40 rows defaulting to standalone, then re-seeded to exactly the four inline rows with 36 standalone. Boot validator green in tiered mode. The re-seed also confirmed the Bleed retune is genuinely carried by the seed script rather than only living in the database. Placement is spliced in by modifier ID at build time rather than widened into the 40-row table, so the four non-standalone rows stay readable instead of becoming a `0` in every tuple's thirteenth position.
- Recorded, not fixed: an out-of-range `effect_placement` value falls through to standalone rather than being rejected by the boot validator. It degrades gracefully and the seed is the only writer today, so a validator range check is worth having but is not load-bearing.

# Item Tiers — gear attribute totals reach the client, and the numbers derived from them stop lying

Issue #69 (epic #36). Equipping an item with a `+STR`-style roll changed nothing on the character screen, because nothing ever told the client. The bonuses were being applied server-side the whole time and genuinely consumed — combat damage, max HP/SP, carry weight and the equip requirement sweep all read `effective_str()` and its siblings — but the only stats-carrying packet is `PacketNotifyLevelUp`, which sends the *base* `m_str` and only fires on level-up, `ForceStatRefresh` and `SettingSuccess`. Never on equip. This is the first of three cycles riding a single Compatibility bump **0.8.0 → 0.9.0**; Server 0.11.0 → 0.11.1, Client 0.8.0 → 0.8.1.

- **A message of its own rather than a widened `ForceStatRefresh`.** Reusing the existing stats packet was the obvious move and the wrong one: its handler also zeroes `m_lu_str` and the rest of the pending level-up allocation, so every equip would have discarded a stat allocation the player had started but not yet submitted. `Notify::GearStats` carries only the six totals and touches nothing else. The base stats stay exactly what they were — the character's own, what creation, level-up and persistence read — and the gear contribution travels beside them rather than folded in, which is also what lets the display split.
- **The totals are indexed by `tier_attribute`, not six named fields, on both sides of the wire.** `CClient::m_add_attribute` was already shaped that way for a stated reason — six named members invited a silently transposed assignment — and the packet and `CPlayer::m_gear_attribute` now mirror it exactly, so filling and reading are loops rather than six chances to write `dex` into the `int` slot. They are `int16` on the wire rather than `uint8`: the per-attribute aggregate cap of 20 is a value in `gamedata.db`, not a guarantee the protocol should bake in.
- **Sent from the equip recalc choke point, which is the whole point.** `calc_total_item_effect` is the one place the totals are recomputed, so the notify goes out from there, gated on the totals having actually moved — the same capture-before/compare-after shape the two Marquee speed bytes already use a few lines below. Unlike those, this goes to the wearer alone, since gear attributes are nobody else's business. The recalc that runs during login can't send it (it is gated on `m_is_init_complete`, which is still false at that point), so `init_player_data` sends one unconditionally right after flipping that flag — otherwise a character who logs in already wearing attribute gear would show nothing until the first re-equip.
- **The client's re-derived formulas were reading base stats too, which is the larger half of the bug.** The character screen and the HUD both recompute max HP, max MP, max SP and max load locally rather than being told them, and every one of those was fed `m_str`/`m_vit`/`m_int`/`m_mag` while the server's `get_max_hp` and friends were feeding themselves `effective_*()`. A `+VIT` roll therefore raised the server's ceiling while the client's bar still read full at the old maximum. `CPlayer` gains the same six `effective_*()` accessors `CClient` has, and all seven of those call sites now read them — the client mirrors the server's inputs rather than approximating them. Angelic deliberately stays its own additive channel, added where it already is, because folding it into `effective_*()` would double-count it at every one of those sites.
- **`InventoryManager`'s equip weight gate agreed with nothing.** It compared against `m_str + m_angelic_str` where the server's matching check uses `effective_str() + m_angelic_str`, so the client could refuse an equip the server would have accepted — flagged during cycle 3-C as a `NOTE for Phase 4 (MUST FIX)` and never ticketed until now. Fixed.
- **Vit and Chr stopped being second-class.** They had no angelic pendant, so they were drawn by two hand-rolled `std::format` lines beside the four stats that went through `draw_stat`. Gear rolls all six, so a `+VIT` roll would have been the one bonus that stayed invisible; they route through the same drawer now. `draw_stat` renders the gear contribution **split** — `18 (+3)`, the owner's call — rather than folded into a single total, so the player can always see what the equipment is actually giving and unequipping stays legible. Angelic keeps folding into the number as it always has.
- Evidence: Windows `-Target All` Debug green, **0 errors and 0 compiler warnings** (the 80 remaining are the cosmetic freetype/SFML LNK4099s). Linux gates run at phase exit with the other two cycles on this bump. /simplify applied inline: `draw_stat`'s two `put_aligned_string` calls collapsed to one. Declined with reasons recorded — the snapshot/compare in `calc_total_item_effect` stays in its current shape because it deliberately mirrors the adjacent speed-bytes precedent, and `CPlayer::effective_*()` stays a mirror of `CClient::effective_*()` rather than a shared mixin, since the two live in different projects over unrelated storage and the shared thing would be six one-line additions.
- Recorded, not fixed: the server's armor stat-requirement gate is internally inconsistent — the STR case reads `effective_str()` while the DEX/VIT/INT/MAG/CHR cases read their base stats, so gear STR counts toward an armor requirement and gear DEX does not. Changing it makes strictly more items equippable, which is a balance call rather than a wiring fix, so it is left as found.

# Item Tiers — Bleed retuned so it reads as a mechanic rather than as a rounding error

Data-only change, applied live with `reload tiers` while players were online — no restart, no version bump. Bleed launched at 5 damage per 2 s for 8 s, which is four ticks and **20 damage total per proc**; against the 3–15% proc band on a Legendary weapon that works out to roughly 3 DPS, and the first live wave reported it as simply not working. It now runs **25 damage per 1 s for 8 s — eight ticks, 200 damage per proc**. Sunder's constants are untouched.

- **This is a spec amendment, not a knob turn, and is recorded as one.** `PLANS/ItemTiers_Plan.md` §5 named "5 dmg per 2 s for 8 s" as Bleed's fixed launch default. The same section frames those constants as `gamedata.db` launch defaults, so retuning them is expected rather than a contract break — but the recorded number would otherwise have gone stale against the seed, so §5 is amended in place with the reasoning and the original value kept visible. `Scripts/seed_item_tiers.py` carries the new values too, so a re-seed no longer reverts the tuning.
- **The tick cadence is only exact on one of the two victim kinds, and that is now written down.** `tick_bleed` fires at most one tick per poll, and its catch-up clause resets to `now + interval` rather than firing a backlog — so a poll slower than the tick interval silently *drops* ticks instead of batching them. NPC victims are polled every 300 ms by `npc_process()`; player victims every 1000 ms by `check_client_response_time()`. At the old 2 s interval that difference was invisible. At the new 1 s interval a player victim is polled exactly at the interval and will occasionally land seven ticks instead of eight. # Item Tiers Cycle 4-D — GM creator dialog: catalog-driven tiered minting

Issue #60 (epic #36). The tester menu's item creator becomes mode-aware. In tiered mode it stops speaking the legacy prefix/secondary bitmask and states a whole instance instead — a Tier, exactly that many modifier slots, an upgrade and a count — with every picker filled from the catalog the server replicated at login. In legacy mode the dialog is what it was. Client-only (0.7.8 → 0.7.9); no wire change at all, since 3-G already shipped `CommonType::TesterCreateItemTiered` and the packet that carries the 15-byte attribute POD — this cycle is the sender that opcode was waiting for.

- **The pickers hold the two structural rules the catalog actually knows, and nothing more.** `min_tier` and `bucket_id` both replicate, so the modifier list for a slot offers only modifiers whose min-tier ladder the chosen Tier reaches, and a Bucket another slot already spoke for is *absent* rather than greyed — offering a pick the server must refuse is not a choice. Changing the Tier retires the slots the new Tier cannot carry, both the ones past the count and any modifier that has climbed out of range, so `count == tier` holds by construction rather than by a check. What the dialog does **not** do is impose anything the catalog cannot justify: per-class eligibility is not enforced (3-G deliberately made it a roll weighting, not a legality rule, so a GM minting a weapon line onto a helm stays a legitimate test instrument), and there is no rarity gate beyond the ladder itself.
- **Bands do not replicate, so the value picker cannot constrain — and the rejection is where a GM learns the window.** `PacketModifierCatalogEntry` carries `multiplier`, `bucket_id`, `min_tier` and the label/format strings; `band_min`/`band_max` and the per-tier windows stay server-side. That is the acceptance criterion "server rejections surfaced to the GM" doing real work rather than being a formality. - **The preview is the real thing, not a description of it.** The dialog builds the attribute POD once and both the preview and the mint packet use it, so what the GM reads is exactly what the server judges. # Item Tiers Cycle 4-C — Animation scaling from the status broadcast

Issue #59 (epic #36). The two Marquee speed bytes the server has been publishing on every status broadcast since 3-D finally have a client that reads them. A cast-reduction wand now visibly shortens the Magic animation and a move-speed cape shortens the walk/run animation *and* the tile slide, for the wearer and for anyone watching them from a second client — the fields ride the shared `PlayerStatus`, so remote entities animate from the same numbers their owner does. Attack, AttackMove, Damage and DamageMove are untouched, per spec §5. Client-only (0.7.7 → 0.7.8); Compatibility stays 0.8.0, since the two bytes have been on the wire since Phase 1.

- **The scaling went in at the one place frame time is computed, so "self and remote" cost nothing.** `CMapData::object_frame_counter` already derives every visible entity's effective frame time from that entity's own tile status — it is where haste and frozen have always been applied — so reading two more bytes off the same `m_status` covers the local player and every remote player through a single edit, with no separate local-player path to keep in sync. The same property makes NPCs a no-op by construction rather than by a guard: an NPC's status arrives through `SetFromEntityStatus`, which zeroes the player-only fields, so `cast_reduction_pct` and `move_speed_pct` are structurally 0 for anything that is not a player.
- **Walk and run now call the shared pacing model instead of re-deriving it.** The client had its own additive haste/frozen frame arithmetic sitting a few lines from `hb::shared::calc::move_frame_time`, which computes exactly the same thing and which the server's anti-cheat move floor is built from. They agreed by coincidence of maintenance, not by construction — and `Player.h` has carried a comment warning that they must never drift since 3-E. The player walk/run branch calls the shared helper outright, so the client's animation and the floor that judges it are now the same expression; the NPC branch keeps the additive path, since NPC base frame times are per-type and are not what the floor measures. Verified equivalent before the swap: `haste_frame_bonus` is `run_frame_time / 2.3` and the player run frame time *is* `run_frame_time`, so the two forms were already identical term for term.
- **The tile-slide duration was a third copy of the same constants, and is now none.** `MovementTiming::WALK_DURATION_MS`/`RUN_DURATION_MS` restated 560 and 312 as literals next to `hb::shared::balance`, which derives both, and next to the anti-cheat floor, which consumes both — the exact drift hazard 3-E left a note about. `EntityMotion::get_duration_for_action` routes Move and Run through `move_interpolation_time` and the two literals are deleted rather than re-derived, which is also what makes move speed reach the slide: the interpolation is what the quick-actions unlock measures at 95% progress, so scaling only the animation would have left the player's command cadence on the old timing. `DAMAGE_MOVE`/`ATTACK_MOVE` stay literals on purpose — attack and damage displacement are not locomotion and move speed must never touch them. Their haste/frozen factors moved from `* 0.7f` / `* 1.25f` to the named `haste_move_duration_pct` / `frozen_move_duration_pct`; both were checked to be bit-identical at both durations (200 → 140/250, 1014 → 709/1267 under either form), so this is a naming change and not a timing one.
- **One primitive expresses the (1 − r), rather than a cast-specific helper.** The first draft added a `cast_frame_time`; the /simplify pass replaced it with `apply_speed_reduction(base_ms, reduction_pct)`, because `move_frame_time` and `move_interpolation_time` were each already open-coding the same clamp-and-floor expression inline. All three now call it, so §5's "× (1 − r)" exists once in the codebase and the clamp cannot be tightened in one place and forgotten in the other two. Cast reduction is applied *after* the mastery adjustment rather than to the raw 88 ms, so a wand shortens whatever the caster's animation actually is.
- Evidence: Windows `-Target All` Debug green, 0 errors and **0 compiler warnings** (the 160 remaining are the cosmetic freetype/SFML LNK4099s). `git diff` verified against the pre-change code to confirm no timing term was lost in the restructure. **The Linux client build has not been run this cycle** — no key access to the CI box from this session — and every acceptance criterion here is something you watch happen (a faster cast seen from a second client, a walk that does not rubber-band, attack animations unchanged), so the visual pass remains the owner's gate.
- **Recorded, not fixed — and it needs a design answer before 4-C's issue closes.** The client still carries two rival movement-pacing models, and they disagree under *haste*: 8 × 54 ms = 432 ms per tile by the frame model against 560 × 0.7 = 392 ms by the interpolation model, of which quick-actions releases the next move at 95% — 372 ms. 3-E's floor takes the `min()` of both precisely because either can gate the next move packet, and its comment said 4-C would unify them. It has not, deliberately: this cycle folded move speed into **both** terms, so the *speed* axis never splits them, but collapsing the haste divergence is a balance decision rather than a refactor. Unifying onto the additive model slows hasted movement from 372 to 410 ms/tile — a live nerf to Haste; unifying onto the multiplicative one speeds the hasted walk animation past the original client's 54 ms/frame, which is where §5's `base × haste(0.7)` composition points but which deviates from retail's animation. The `move_tile_time` comment now states the open question instead of promising a fix that did not land.

# Item Tiers Cycle 4-B — World presentation: tier beams, colored pickup line, tint gating

Issue #58 (epic #36). A tiered drop is now visible from across the screen before anyone walks over it: every tiered ground item raises a light column in its Tier color, faint neutral for Common and brighter with rank. The pickup line renders the item name in that same color, and the sprite dye-tint channel closes in tiered mode so a tier is read from color-of-light and color-of-name rather than from a recolored icon. No broadcasts, no banners, no floating labels — spec §11 as written. Client-only (0.7.6 → 0.7.7); Compatibility stays 0.8.0, since the tier byte has ridden the ground-item and map packets since 1-C.

- **The beam is a procedural column, not a new effect — the Pick, now recorded in the plan.** The effect list exists for transient animations that run to a frame count and retire themselves; a ground item persists until someone takes it, so an effect-backed beam would need lifetime tracking against tile state, new art, and would drift out of sync every time a tile changed off-screen. `Screen_OnGame::draw_tier_beam` instead draws from the tile's own data inside the ground-item pass, which makes it self-healing by construction: the tile is the single source of truth, and a tile that stops holding a tiered item stops drawing a beam on the next frame with no bookkeeping at all. Shape is a full-height pillar: a soft ground pool, a bright tapering root, and a narrow shaft dissipating to the top of the screen, with a slow pulse, blended additively so it reads as light over whatever the tile already drew instead of as a painted rectangle. Drawn *before* the item sprite, so the item sits in front of its own light. Drawing inside the tile pass is also what makes a full-height shaft legible without a second pass: a pillar painted at this row covers the rows already drawn above it — the ones behind it — and is painted over by the rows drawn after, the ones in front, so occlusion is correct for free. All four tiers raise a pillar and the per-tier alpha ramp does the grading, so Common stays a faint neutral thread while a Legendary dominates the screen.

- **Additive light desaturates toward white, which is why the blue tier looked white.** Found in the first visual pass. `dst + src` raises every channel, so a color whose channels are all high adds *brightness* rather than *hue* — Legendary's gold reads correctly because its blue channel is 16 and it therefore barely touches that channel, while Epic's 150/160/225 raises all three nearly equally and arrives as a washed-out white indistinguishable from Common. `beam_light_color` strips 80% of the shared white component and renormalizes to full brightness, so Epic emits 72/97/254 and Rare 72/255/72, while Common — pure white, no chroma to extract — passes through untouched and stays the faint neutral §11 asks for. **The replicated tier color is not modified**: this is the light the pillar emits, a beam-local derivation, and names keep rendering in the exact color the server sent. The alpha ramp also rose `{30,55,80,110}` → `{55,110,150,195}`.
- **Stacked rectangles are why it looked pixelated, so the pillar is gradient quads now.** A filled rect has a hard one-pixel edge; the world draws at logical resolution into a `setSmooth(false)` back buffer that blits 1:1 in windowed mode, so that edge reaches the screen exactly as authored — no amount of tuning alpha fixes a shape whose sides are a step function. New primitive `IRenderer::draw_gradient_quad` takes an arbitrary quad with a per-corner color and emits one GPU-interpolated draw, so each section of the pillar is a quad pair whose centre line carries the color and whose outer corners sit at alpha 0. That buys a per-pixel falloff *across* the pillar as well as along it, and it is cheaper than what it replaced: 8 quads per pillar against ~15 rects, and against the ~45 that soft edges would have cost had they been built from rects. Like the `BlendMode` parameter added to `draw_rect_filled` earlier in this cycle, it is a general primitive rather than a beam-specific entry point.
- **`IRenderer::draw_rect_filled` gained an optional `BlendMode`** rather than the beam hand-rolling additive draws out of `draw_line`, which already had exactly that parameter — the primitive API was asymmetric, and closing that gap is cheaper than working around it. Default `Alpha`, so every existing caller is unchanged; `SFMLRenderer` is the only implementor.
- **Beam color is data; beam intensity is not, deliberately.** The column reads its color from the replicated tier-presentation table through a new `item_name_formatter::tier_row` accessor — the same lookup `apply_tier_presentation` uses, so an unreplicated row demotes to *no beam* exactly as it demotes to a plain item name, one rule for missing presentation data everywhere. The per-tier alpha ramp stays a code table: promoting it to data needs a wire field, and Phases 2–4 are wire-frozen. Recorded in the plan as a Phase-5 candidate rather than left implicit.
- **The pickup line got a colored span, not a colored line.** §11 asks for the *name* in Tier color inside "You got a {name}." — the surrounding sentence stays chat-colored. `EventEntry` therefore carries an optional `event_highlight` (offset, length, color) and the renderer splits the draw into prefix / name / suffix, measuring each run to advance. This is a general mechanism on the event list rather than a pickup-specific special case, which is what let the two lists share one implementation: `show_events` previously carried the *same* seven-case color switch twice, once per list, and both collapse into a single `event_color` table plus one line drawer. The switches had no `default`, so an unlisted color index drew nothing at all — preserved exactly, as a null color rather than an accidental fallback. The name offset is found with `rfind`, since the name is the last thing the template substitutes.
- **The tint gate closes a palette band, not a mode-shaped branch at each draw site.** Palette entries 16-21 exist for exactly one reason — they are the legacy strategy's prefix tints, written by `attribute_prefix_types.weapon_color` and by the GM mint switch — so in tiered mode `CGame::draw_item_sprite` zeroes that band and nothing else. Player and config dyes (1-15) keep working, and a legacy item minted before a mode flip stops tinting too, which is what "sprites are never tinted in tiered mode" literally says. One gate covers every icon and ground sprite in the game because that function is the single shared draw path. `worn_tint_params` needs no gate at all: worn colors are 4-bit on the wire (`Appearance.h`, `(iApprColor >> 28) & 0xF`), so the prefix band can never reach it — verified rather than assumed.
- Evidence: Windows `-Target All` Debug green, 0 errors and **0 compiler warnings** (the 160 remaining are the cosmetic freetype/SFML LNK4099s). The tint-band reasoning was checked against the live data — `attribute_prefix_types.weapon_color` in `gamedata.db` is 16-21 for every prefix that tints, the single exception being prefix 10 mapping to regular dye 5, which is outside the band and therefore keeps its tint by design. **The Linux client build has not been run this cycle** — no key access to the CI box from this session — and the beams, the colored pickup line and the absence of tint are all visual, so the Phase-4 visual pass in both modes remains the owner's gate.

Reviewed and declined: extracting a shared "draw N colored runs on one line" helper — `TextFieldRenderer` (selection highlight) and `ItemTooltip` (label + value) already open-code the same measure-and-advance idiom, so the third occurrence is a real generalization candidate, but it lives in two files outside this diff and is a text-layer refactor rather than a cleanup of this change.

# Item Tiers Cycle 3-G — GM item creator (server): mode-aware minting with legality enforcement

Issue #56 (epic #36). The GM creator stops being a code path that writes whatever the client asked for and becomes a request the server *judges*. In tiered mode a mint states a Tier and up to four modifier slots and must survive the same structural audit a rolled drop does — count == tier, one modifier per Bucket, the min-tier ladder, Band/window bounds — plus the two scope rules a roll gets for free (tierable gear only, never a named unique). In legacy mode the creator behaves exactly as it did. Every mint, in either mode and from any chat venue, now writes an economy-audit line. Server-only (0.10.3 → 0.10.4); Compatibility stays 0.8.0.

- **Legality lives in the Roll-strategy seam, not in the handler.** `roll_strategy` gains `mint(item, requested)` returning an empty string on acceptance and the violation otherwise, because what a legal instance even *looks like* is precisely what the two strategies disagree about — the same reason `roll` is virtual. `RollStrategy.h` had anticipated this since 3-A ("GM minting routes here in 3-G"). The tiered implementation calls `validate_tiered_instance` rather than re-deriving the rules: that function was written in 2-D as the shared gate, deliberately mirroring the spec instead of the roll code so a roll bug cannot self-certify, and #51 left an explicit note not to re-implement it. The rollsmoke harness and the GM creator are now its two callers, which is what keeps a minted Legendary and a dropped Legendary structurally the same object.
- **Per-class `modifier_eligibility` is deliberately *not* a legality rule.** The gate's signature is class-blind by design, and §10 enumerates the structural rules without it — eligibility weights what may *roll* on a class, so a GM minting a weapon line onto a helm is a legitimate test instrument rather than an illegal item. The two rules that *are* item-shaped live in the tiered mint beside the gate call: an item outside §1 scope cannot carry a tier at all, and the `is_special_item` roster is excluded exactly as it is at roll time.
- **A tiered mint is a specification, so nothing is derived from it.** `apply_modifier_derived_stats` is not called and no dye tint is applied — mirroring `tiered_roll_strategy::roll`, per §6.5/3-C (tiered stored stats never mutate) and §11 (tiered gear never tints). The legacy mint keeps both, including the hardcoded `item_color` 16–21 prefix switch moved verbatim out of the handler: that mapping is an owner-blessed deviation (fork issue #2) and it disagrees with `m_modifier_weapon_color` on Special (18 vs 5), so reconciling them stays issue #2's call rather than a silent side effect of this cycle.
- **Tiered mode refuses a legacy-shaped mint instead of quietly accepting one.** The pre-4-D creator dialog packs prefix/secondary nibbles into a bitmask; in tiered mode that request is rejected with "modifiers require a tier (1-4)" while a plain mint still works, so the interim state is honest rather than producing untiered items carrying tier-system modifiers.
- **The tiered request gets its own command id rather than more fields on the old one.** `CommonType::TesterCreateItemTiered` + `PacketCommandTesterCreateItemTiered` carry the 15-byte attribute POD; the existing `TesterCreateItem` layout is untouched and old clients are unaffected, so Compatibility stays 0.8.0. Reusing the unused `text`/`v4` tail of the existing packet was rejected on evidence: `ConcurrentMsgQueue::pop` copies only the bytes a client actually sent into a buffer it does not clear, so trailing fields of the short legacy request read **stale bytes from the previous message** — a legacy mint could have been misread as tiered. The command id sits in the first bytes, so it is the one field that is always real. Cycle 4-D fills the struct in from the dialog.
- **Every mint is logged, and rejections are logged too.** New `ItemLogAction::GmMint` on the `trade` channel carries GM, IP, quantity, position and the full instance; `format_item_info` grows a `(tier=N id:v:v2 ...)` clause when a tier is present, since it only ever printed the first two slots and an audit of a four-line Legendary needs all four. Legacy lines are byte-identical (the clause is appended, and only when a tier exists). The audit covers the chat creation venues too, not just the tester menu: `/createitem`, `/giveitem` and the bulk helper the two share. The operator-facing `[GmMint]` line on the `commands` channel is the only record of a **rejected** attempt — the interesting case when a client is crafting packets.
- **`mintcheck` is the new headless prover.** `mintcheck <item_id> <tier> [mod_id:value[:value2] ...]` runs a spec through the running mode's gate and prints `MINTCHECK <id> <tier> OK|REJECT <reason>` without creating anything or needing a connected player — the same role `rollsmoke` plays for the drop roll, and what makes "illegal mints rejected server-side" provable headlessly on both platforms instead of only by hand. `/createitem` gained the same spec syntax so a GM can attempt an illegal mint from in-game, which the 4-D dialog will not let them do.
- Evidence: Windows `-Target All` Debug green (0 errors, 0 compiler warnings — the 80 remaining are the cosmetic freetype/SFML LNK4099s). Boot smokes green in both modes; a 2000-roll tiered rollsmoke still reports 0 legality violations, so the shared gate did not shift under its other caller. The gate itself was exercised through `mintcheck` in both modes: **tiered** — a legal Legendary dagger (`4 1:7 6:5 11:2 34:3`) accepted, and one rejection per rule (count != tier, two modifiers from one Bucket, a `min_tier 4` modifier at tier 1, a value outside its Band, a tier on an accessory, a tier on a Kloness Blade, modifiers with no tier); **legacy** — a tier rejected outright, a third slot rejected, prefix+secondary accepted. The dev `gamedata.db` was left in legacy mode as found. **The Linux server build has not been run this cycle** — no key access to the CI box from this session — and the mint round-trip through the tester menu needs a running client, so both remain the owner's gate.

# Item Tiers Cycle 3-F — Drift fixes #1–#5 (data-driven enchant, MC/CC, Righteous, Kloness)

# Item Tiers Cycle 4-A — Data-driven item names and tooltips with the Tier word and Tier color

Issue #57 (epic #36). The client's item-name formatter stops reading two fixed attribute slots and starts reading all four modifier slots of the spec §12 POD, ordering their tooltip lines by the catalog's Bucket, and rendering the Tier word and Tier color from the replicated presentation table. Every player-facing string a rolled modifier produces now comes from the server — the last hardcoded modifier strings are deleted, and a row the server never replicated shows its raw roll instead of quietly vanishing. Client-only (0.7.5 → 0.7.6); Compatibility stays 0.8.0 — everything this cycle needs shipped in the 1-D catalog packet.

# Item Tiers Cycle 3-E — Speed-aware anti-cheat posture; move check downgrades to log-only

Issue #54 (epic #36). The move check stops asking "did this player cross a tile in under 200 ms" and starts asking "did this player cross a tile faster than *this* player legally can" (spec §5, drift #6). The flat-200 ms disconnect at `Game.cpp` becomes a per-player floor derived from the client's own pacing, and it **logs instead of disconnecting** — posture is a `tier_settings` row, not a build. The cast floor 3-D made per-player gets the same knob. Server-only (0.10.0 → 0.10.1); Compatibility stays 0.8.0.

- **The flat 200 ms was already disconnecting legitimate players.** A hasted run is 8 frames × 23 ms = 184 ms per tile, so every hasted runner tripped a check they could not avoid — the bug was invisible only because haste plus running is a narrow window. At the other end it was far too permissive: a walk is 560 ms per tile, so a walk-speed hack could run at 2.8× and never register. One constant cannot serve both, which is the argument for the per-player floor rather than a retuned constant.
- **The floor is the faster of the client's two unlock paths, not one of them.** This is the load-bearing detail. The client releases the next move command either on animation completion (`move_frames` × per-frame time, where haste/frozen adjust the *frame* additively — `MapData.cpp`) or, with quick actions enabled, at 95% of the interpolated slide (where haste/frozen scale the whole *duration* multiplicatively — `EntityMotion.cpp`). The two models agree with no status effects and diverge under haste: a hasted walk is 432 ms by frames but 372 ms by interpolation. A floor derived from the frame model alone lands at 367 ms against a legal 372 ms cadence — a 1.4% margin that ordinary jitter would trip, turning the grace factor into a fiction. Taking the minimum restores the intended ~17% margin uniformly across walk, run, haste, frozen and speed-geared states. Cycle 4-C unifies the client onto one model, at which point the two terms collapse into one.
- **A gap is scored against the motion that produced it.** The measured interval is the duration of the *previous* move, so `m_was_running` remembers which pacing to use. Scoring a run's 312 ms gap against the 476 ms walk floor would flag every player who stops running — the most common movement pattern in the game.
- **Posture is data because log-only is a measurement phase, not a permanent state.** `posture_move` / `posture_cast` (`log` | `disconnect`) and `move_grace_pct` are the rows 2-E already seeded; they resolve once at load into `tier_config::anticheat` so the per-packet path reads plain fields. Escalating a check once live data shows the floors are clean is a `reload tiers`, not a deploy. The boot log states the posture the server actually *resolved*, not what the DB stores — a malformed row falls back to the code default, and the difference is exactly what an operator needs to see.
- **The validator refuses a typo'd posture in both modes.** A bad value silently falling back to `log` would be harmless; falling back the other way would not, and either way the DB and the running server would disagree about a rule that disconnects players. `tier_config::parse_posture` is the single owner of the vocabulary, so the loader and the validator cannot drift on what a legal value is. `move_grace_pct` outside 1..100 is likewise fatal — 0 makes every legal move a violation, and above 100 the floor exceeds the client's own pacing and does the same.
- **Log-only removed the thing that bounded the log.** A disconnect was, incidentally, a rate limiter: one line per offender, then they were gone. Without it a persistent offender emits a security line on every move packet for the whole session, and each line takes the process-global log mutex, formats a timestamp and flushes to file and console — a stall for every other thread that logs, not just the mover. Violations are now counted on the client and logged first-then-throttled, with the running count in each line. Measuring a floor wants a rate, not ten thousand identical lines. The cast check inherits the same treatment.
- **The movement pacing math moved to `Shared/`** (`hb::shared::calc::move_frame_time` / `move_interpolation_time` / `move_tile_time`, over new `BalanceConstants.h` entries) because a server floor that disagrees with client pacing is a false-positive generator by construction. `PlayerAnim::Move`/`Run` in the client now source their frame times and frame count from those same constants, so the "8 frames × 70 ms / 39 ms" relationship has one home instead of three.
- Fixed in passing: `m_move_freq_time`, `m_magic_freq_time`, `m_attack_freq_time` and `m_is_move_blocked` were never initialized in the `CClient` constructor. A garbage `m_move_freq_time` makes the first move packet's gap arbitrary — which the check reads as a speed violation, and which under the old code was a disconnect on login.
- Evidence: Windows `-Target All` Debug green (0 errors, 0 compiler warnings — all 81 are the cosmetic freetype/SFML LNK4099s); Linux **server and client** both green on `~/hb38-ci/` with zero GCC warnings. Boot smokes green in both modes with the posture line reporting `move=log cast=log`, and the dev `gamedata.db` restored byte-identical to HEAD afterward. The posture knob is verified to flip behavior with no rebuild (`posture_move` → `disconnect` reports `move=disconnect` on the next boot). Negative tests confirm the validator refuses `posture_move='warn'`, `posture_cast='warn'` and `move_grace_pct` of 0 and 101, each with a precise message, and blocks the boot. Computed floors are checked against every status combination rather than asserted. The live checks — moving and casting at legal speeds with rolled gear and confirming a silent security channel, then injecting speed and confirming a log line with no disconnect — need a running client and are the owner's manual smoke.
- /simplify 4-agent pass applied. The load-bearing catch was the rival-pacing-model divergence above, which three of the four agents converged on from different angles and which turned out to be a real correctness problem in the floor, not a tidiness issue. Also applied: one owner for the posture vocabulary, the violation-log throttle, `PlayerAnim`'s `max_frame` derived from `balance::move_frames` instead of a literal 7 plus a comment, and the haste frame bonus named rather than re-deriving `39 / 2.3` at each site. Declined with reasons recorded: dropping `m_was_running` and always scoring against the run floor (defensible against a relabelling attacker, but it abandons the spec's per-motion floor and loses real signal during the measurement phase this cycle exists to serve); converting the constructor assignments to in-class initializers (correct direction, but `CClient` assigns several hundred fields in its constructor and five in-class exceptions would read as an accident); and unifying all four frequency checks — move, cast, and the two near-duplicate swing checks in `Game.cpp` and `CombatManager.cpp` — behind a single evaluator owning grace, posture and log format. That last one is the right generalization and is now recorded as a follow-up: as built, giving the swing checks a posture means inventing a third and fourth grace idiom, whereas with an owner it would be two rows of data.

# Item Tiers Cycle 3-D — Marquee mechanics (Sunder, Bleed, drains, cast/move speed)

Issue #53 (epic #36). The six spec-§5 Marquee behaviors stop falling through `apply_modifier_totals`' `default:` and go live server-side. **Sunder** and **Bleed** are proc-on-hit debuffs rolled per landed hit; **MP/SP drain** are always-on and deterministic; **cast-time reduction** now shortens the server's own per-player anti-speedcast floor as well as the animation; **movement speed** is summed, clamped and published. All four weapon exotics work on players and NPCs alike, and no broadcast bit was added for them — victims learn about them from notify lines, exactly as §5 specifies. The two speed fields on the status broadcast, zero since Cycle 1-C, now carry real values, so Cycle 4-C has something to scale animations from. Server-only (0.9.9 → 0.10.0); Compatibility stays 0.8.0 — the wire fields all shipped in Phase 1.

- **Every launch constant is data.** Sunder's −50 / 5 s, Bleed's 5 damage / 2 s / 8 s, and the 1500 ms cast floor come from the `tier_settings` rows 2-E seeded, resolved once at config load into `tier_config::marquee` so the proc and cast paths read plain ints rather than doing a string-keyed map lookup and a throwing parse per hit. A `reload tiers` retunes them without a restart, and an active debuff carries the delta and period it was *applied* with, so a mid-flight reload cannot retune a debuff already ticking.
- **Bleed shares nothing with poison, deliberately** (spec §5): fixed tick versus `dice(1, level)`, refresh versus blocked-while-poisoned, no poison-resist check, no Cure. A weapon may roll Poisoning *and* Bleed — they sit in different Buckets — and a victim carries both at once. Refresh extends the duration but leaves the tick cadence alone; restarting the clock on every proc would let a fast weapon refresh a bleed forever without a single tick ever landing. The tick that falls exactly on the duration boundary is settled *before* expiry is considered, so the fourth tick (8 s / 2 s, ~20 damage per proc) is not silently swallowed whenever the tick loop arrives a millisecond late.
- **A bleed tick can land the killing blow** (owner decision this cycle) — but only while its source is still identifiable. Only equipped gear carries rolled lines and only players equip, so a bleed's attacker is always a player; the handle is stored beside the attacker's name and both must still agree when the tick lands. Eight seconds is long enough for a reconnect to inherit a recycled handle, and `client_killed_handler` dereferences a Player attacker handle unguarded — so an unverifiable bleed leaves the victim at 1 HP instead of killing them anonymously. Player kills route `analyze_criminal_action` + `client_killed_handler`, NPC kills route `on_entity_killed`, so PK flagging, exp and loot behave exactly as they do for a melee kill.
- **Drains take, they do not give** (owner decision this cycle): §5 prices them as resource denial, not sustain, so the attacker gains nothing. The stamina half goes through the existing `effect_sp_down_spot`, which means a Marquee weapon respects Firm Stamina and the invincibility slate like every other SP-drain source in the game. NPCs hold a live mana pool but have no stamina, so SP drain has nothing to take from them — recorded, not an omission. The per-hit notice line is throttled to one per 3 s per victim; the two procs are discrete events and notify every time.
- **Sunder lands where defense ratio is read, not where it is stored.** `sunder_defense_delta` is queried at hit resolution instead of being written into the victim's stat block, so expiry needs no timer and nothing can leak into a saved character. It applies *after* the back-attack halving — "−50 defense ratio" is a flat step, and applying it earlier would quietly halve the debuff too — with the existing `< 1` floor keeping a sundered target from becoming impossible to miss.
- **The cast floor became per-player.** `check_client_magic_frequency`'s hardcoded 1500 ms is now `cast_check_floor_ms × (1 − r)` from the wielder's own wand, because a Legendary wand shortens the cast animation and would otherwise trip the check its owner paid for. The posture stays log-only (Cycle 3-E owns the `posture_*` knobs and the move check); the violation log now carries the observed gap, the computed floor and the player's reduction, so false positives are measurable.
- **Movement speed is clamped twice**, per §5: 10% per item and 20% across the set. `move_speed` is the one catalog row whose `aggregate_cap` (20) exceeds its `band_max` (10), so the per-item half is the only place that needs saying — everywhere else the aggregate clamp already implies it. A recalc that actually moves either speed byte rebroadcasts the status the way every other status change does, gated on `m_is_init_complete` so the login handshake is not duplicated.

### Animation from the art already in hand
First in-game test read as "paper sliding across the screen" — correctly, because every frame of a sprite was identical while its screen position interpolated, so only the position moved. Fixed without new renders: each facing already has **two** genuine poses, its own action render and the standing render, so every action now cuts between them.
- Idle now breathes. Every shipped mob does — measured silhouette change across their idle frames is dire-boar 0/2/11/18/18/11/3/0%, centaur peaking at 53%, hellhound 45%, while the griffin sat at a flat 0%. A single render cannot move limbs, so the body is stretched a few px upward from a planted baseline on a rise-and-fall arc, which reads as breathing and costs nothing. Scaling rather than shifting a region avoids a seam across the shoulders; the rect height and pivot are constant across the frames so the feet never leave the ground. Peak is ~10% — deliberately under dire-boar's 18%, whose figure comes from real limb movement, so matching it with a whole-body stretch would look rubbery.

- attack `[stand, strike, strike, stand]` — a lunge and recovery rather than a frozen talon-swipe.
- damaged `[flinch, flinch, stand, stand]`, die `[stand, collapsed, collapsed, collapsed]` — a fall instead of the corpse popping in.

# Vince the Auctioneer gets his own sprite (first AI-assisted NPC)

Vince has been shipping since the Trading Post landed, but with no art of his own — the client drew him with a stand-in built from the *player* compositor (a female body in full plate with green boots and a green cape). He now has a real pak, and the whole stand-in is gone.

### Client data
- `sprites/npcs/vince.pak`: new town-NPC pak — 8 sprites (one per facing) × 8 idle frames, 64 px tall, feet-centre pivots with william's 5 px overhang (foot anchor taken from the bottom 8% of rows, not the bbox centre, or he slides sideways as he turns). Built from a three-view pre-rendered 3D sheet (front, right profile, rear) plus mirrors for W/SW/NW; NE and SE substitute the N and E art for now. Idle animation is a synthesised 1 px head settle over the 2 s cycle.
- Pipeline notes, all learned by measuring against the shipped town NPCs:
  - **Palette** — the originals carry ~220-240 unique colours per frame (pre-rendered, not pixel art), so the 24-colour item-icon quantize flattens the face to a single tone. One shared 160-colour palette across all facings, built from opaque pixels only (feeding median-cut the background block lets it hog palette boxes).
  - **No outlines, ever.** The originals have none. The first attempt used cel-shaded illustration renders and added silhouette edge-darkening on top; the useful metric is the fraction of body pixels that are *thin dark lines* (much darker than their local neighbourhood) — originals sit at 2.9-10%, the illustration source hit 12.8%. Counting near-black pixels outright does not work: it cannot tell dark art from outlined art. Edge-darkening is off, and the source is now a 3D render that scores 5.9%.
  - **Brightness is solved, not hard-coded.** Renders arrive dark, but how dark varies per generation — two sheets of the same character came in at mean luma 42 and 56 — so a gamma tuned on one blows out the next. The lift gamma is now searched across all facings at once to land the set on 84 (tom and gandalf are 82.5, howard 85.7; william is an outlier at 143.9). The search has to include the contrast step, since PIL blends toward a grey averaged over the whole image including the transparent region, which is near-black here and pushes the body ~7 luma brighter.
  - **Lift luminance, not RGB.** The gamma runs on luma and is applied back as a per-pixel scale factor across all three channels, which leaves saturation exactly as rendered. Running it on RGB directly drags every colour toward white: an earlier pass lost saturation 0.526 → 0.463 and read as if white paint had been brushed over him. Fixed, it sits at 0.62 against the originals' 0.36-0.52.
  - **Match the originals' surface smoothness, measured as local contrast** — the mean luma step between adjacent body pixels. This is what separates a sprite that reads as a solid volume from one that reads as a flat patterned shape, and it is not the same thing as overall contrast. The shipped mobs sit at dire-boar 17.2, ogre 17.5, troll 18.8, ettin 19.1, centaur 25.5: ettin's skin is one continuous tonal sweep per muscle, so the eye integrates it into form. At the 140% unsharp inherited from Vince the griffin measured 31.6 — 65% noisier than ettin — because every feather edge survives the downscale as a hard pixel step and reads as texture rather than shape. Detail at 78 px does not stay detail; it becomes noise that flattens. Dropped to 40% unsharp, landing at 20.8.
  - **Sharpen the body, not the face.** Photorealism does not survive to a 19 px head, but sharpening it does — the unsharp mask manufactures eyes, cheekbones and beard edges the originals do not have, and the face reads as a portrait beside their suggestions of one. The mask is held off the top 28% and feathered in across the shoulders. With that in place the head measures 258 px in 60 tones (spread 44.7) against william 240/96/45.8, tom 257/99/49.0, gandalf 269/113/52.6 and howard 305/126/65.2 — i.e. less facial detail than any original, which is the bar that matters. A photoreal source still *looks* photoreal at full size; that impression does not reach the sprite.

- `Screen_Loading.cpp`: registers `npcs/vince` at slot 101. The slot is fixed by the owner type, not the next free index — the body sprite is derived as `Mob + (owner_type - 10) * 8 * 7` and `owner::auctioneer` is 111.

Verified against both original source trees (HelbreathServer and HB382_CENTUU): the leak never had this — its spot generators refill all maps unconditionally and the entire progression chain (`OpenApocalypseGate`, the `ApocalypseMobGenType == 2` boss trigger) is commented-out stubs. Implemented per official behavior as described by Nick.

### Server
- New `CEntityManager::apocalypse_suppresses_spawns(map_index)`: while Apocalypse mode is active, both spawn paths (spot generators and the random mob generator) skip maps with `apocalypse_map` set and `apocalypse_mob_gen_type != 0` — exactly inferniaa, inferniab, procella, abaddon. Maze and Druncnian City (`gen_type = 0`) keep regenerating, matching their traverse-only role.
- Between events the generators run normally, so each apocalypse starts with fully populated maps. Kill-time/decay counters are untouched — the suppression is a pure computed predicate, so no state can desync when the event ends mid-corpse-decay.

### Versioning
- Server → 0.8.3 (server-only).

# /clearnpc: optional "rewards" flag (exp/drops), gated by its own admin level

### Server
- `/clearnpc rewards` (combinable with `all`, any order) attributes every kill to the admin as attacker, so the normal death rewards fire: exp share, loot rolls, quest credit — and the type-81 `AbaddonKilled` broadcast, which makes boss-death paths testable via the command. Without the flag, kills stay attacker-less (no exp/drops), as before.
- The flag is gated by a new **sub-permission** `clearnpc.rewards` in the existing `admin_command_permissions` table, seeded at default level 1000 (Administrator) while base `/clearnpc` stays 500 (Developer). Tunable like any command via the DB or `setcmdlevel clearnpc.rewards <level>`; dotted keys can never collide with real command dispatch. An under-leveled admin using the flag gets a notice with the required level.
- `CEntityManager::kill_entities_on_map` gained an `attacker_h` parameter (0 = system kill) — no new reward logic; the flag just selects the attacker identity the existing death path already branches on.
- `setcmdlevel` listing now prints sub-permission keys without the `/` prefix so they don't read as typeable commands.

- Server → 0.8.2 (server-only).

# Admin command: /clearnpc — kill all NPCs on the current map

New admin chat command, built for event testing — e.g. simulating players clearing Apocalypse maps (Infernia → Maze → Procella → Abaddon progression) without hand-killing hundreds of mobs.

### Server
- `/clearnpc` kills every monster (side 10), summon, and spot-generator mob on the admin's current map. `/clearnpc all` additionally kills static town/faction NPCs (shopkeepers, guards, gates) — those spawn once at boot, so the reply warns they only return on server restart.
- Kills route through the shared death path (`on_entity_killed` with no attacker — the summon-expiry / war-teardown idiom): death animation, corpse and decay, natural respawn cycle, and the same `m_total_alive_object` bookkeeping player kills drive. No exp and no drops (both are attacker-gated), so the command can't be farmed. Explosive mobs still detonate on death, as they would for a player kill.
- New `CEntityManager::kill_entities_on_map(map_index, include_static)` owns the map-scoped kill loop and the static-vs-regenerating classification; the command class is a thin arg-parse + notify shell like `/spawn`.
- Default permission: Developer (500), GM mode required; seeded into `admin_command_permissions` on first boot like every command, adjustable in the DB.

### Versioning
- Server → 0.8.1 (server-only; chat commands ride the existing protocol — no compatibility bump).

# Faithful frozen recolor + weapon afterimage (completes issue #3 code work)

Replicates the original DDraw client's two **scaled-base** special-case draws — the last code items on the #2/#3 faithful-coloring workstream. Both now use the additive-offset blends (`offset_tinted`/`additive_tinted`) that #21 established for worn gear, instead of the multiplicative stand-ins, so sprite highlights survive.

# Worn equipment coloring: original additive-offset dye (fixes DK/DM flat-black armor)

Resolves issue #21 — the worn-equipment slice of the #2/#3 faithful-coloring workstream. Gear on in-world characters and the character select/create preview was tinted **multiplicatively** (`DrawParams::tint`), which scales each texel by `palette[color]/255` — crushing a 255 specular highlight to 40 for the Dark Knight/Mage armor (palette entry 6 = 40,40,40) and rendering it flat black. The original DDraw client (and the already-fixed inventory icons, `draw_item_sprite`) instead **add a signed offset** `clamp(src + palette[color] - palette[0])` (base = regular index 0, gray 100,100,100), which preserves highlights for the glossy dark look.

### Client
- New `CGame::worn_tint_params(color, weapon)` — the original PutSpriteRGB additive-offset dye, mirroring `draw_item_sprite`'s math so worn gear matches its icon. Weapon colors 1-9 read the weapon sub-palette (dual-palette rule); armor/shield/mantle/pants/boots/arm/helm read the regular table. Worn colors are 4-bit (0-15); color 0 = plain draw (unchanged).
- `RenderHelpers.cpp` (`draw_equip_layer`, `draw_weapon`, `draw_shield`) and the menu-preview path (`draw_object_on_move_for_menu`) now route through it. Hair keeps its extended-palette (32-47) absolute tint per #3.

### Engine (SFMLEngine)
- The additive-offset fragment shader now multiplies its result by `gl_Color` (was applying only `gl_Color.a`), and the offset draw path no longer force-overwrites the sprite color to white. Together these let night-mode darkening (and alpha) reach offset-tinted draws, so worn gear keeps dimming at night in step with the body it sits on. Backward-compatible: existing offset callers pass white RGB (a no-op multiply), and item icons (no alpha-effect) are unaffected.

### Not changed (remaining #3 follow-ups)
- Weapon/shield glare overlays and berserk glow are untouched; the original's scaled-base special-case draws (−base/2 berserk, −base/3 afterimage) are not yet replicated.

# Fix: Dark item majestic evolution stages now actually fire

### Research findings (vs HB382_CENTUU)
- The majestic upgrade **cost formula was already faithful** on both sides: `x(x+6)/8 + 2` points at level x (2, 2, 4, 5, 7, 8, 11, 13, 16, 18, 22, 25, 29, 32, 37) — server routes and the client upgrade dialog agree. Not n+1.
- The **stat gates were already faithful**: `equip_item_handler` enforces the original per-stat armor requirements (`item_effect_value4/5`; the Dark Mage Robe requires MAG 100, same as wizard robes) plus the weight rule (`weight > STR x 1000` — Dark Knight Plate Mail needs STR 100). The original gates at equip time, not at claim time; most DK/DM pieces carry no stat requirement in any legacy data.
- The **evolution stages were dead code in CENTUU itself** (inherited by our port): the handler rejects items already at +15 before the `== 15` transform branches can run, so only staff→wand at +11→12 was ever reachable. The 746→892 stage references an item defined in no known config or DB — had it ever fired it would have destroyed the wand.

### Server (ItemManager.cpp)
- Wand line now completes: Dark Mage Magic Staff → Magic Wand at +12 (unchanged), Magic Wand → **Dark Mage Templar** on the upgrade that reaches +15 (re-anchored from the unreachable `== 15` to `== 14`). The 892 branch is removed; the Templar is the final stage.
- Sword line now has its stage: Dark Knight Giant Sword → **Dark Knight Templar** on the upgrade that reaches +15, mirroring the wand line. Designed deviation: legacy data ships 737/745 with identical stats (the stage is the prestige appearance) but no legacy source ever wired the transform.
- Legacy bug fix: the female Dark Mage Magic Staff (732) was excluded from the staff→wand transform (only 714 was checked) and could never evolve.
- Great Sword, Flameberge, and Rapier have no evolution in any legacy source — left as plain majestic-upgradeable, matching CENTUU.

# Fix: shutdown double-free of every NPC (SIGSEGV)

### Server
- `CGame::m_npc_list` is an alias into `CEntityManager`'s entity array, yet `CGame::quit()` (and the re-init sweep in `CGame::init()`) deleted the NPCs through it without nulling the slots — `~CEntityManager`, the real owner, then deleted them all a second time. # Trading Post server escrow core (Phase 2)

### Trading Post (Server / escrow store)
- Built the server-side escrow store for the Trading Post — phase 2 of the build (no request handlers, hooks, NPC content, or client dialog yet; the core functions have no callers beyond startup wiring). # Frozen players no longer disconnected by the swing-speed anti-hack

### Bug Fixes
- Fixed an intermittent client disconnect (seen as `Game socket drain_to_queue failed: -1`) that happened when a player was frozen — e.g. by a Frost or Nizie — and swung in quick succession during the ~5s freeze. Root cause was server-side: the swing-speed anti-hack checks inflated the *minimum* legal time between swings while `frozen` (`effective_swing += frames * (bft >> 2)`), but the client never slows attacks when frozen (only movement). So swinging at the normal rate fell under the inflated threshold, tripped the "Swing hack" / "Batch swing hack" detector, and the server called `delete_client` on that one player. Removed the `frozen` term from **both** checks — `CombatManager::check_client_attack_frequency` and the 7-attack batch check in `Game.cpp`. Haste still lowers the threshold; real speed hacks are still caught.
- This matches the original game source (`HGServer`): the original player swing check is a flat 3500ms / 7-attacks rule with **no** status terms, and the original never slows a frozen *player's* attacks — the 50% action-time slow is **NPC-only** (`NpcProcess`). Frozen remains movement-only for players.

### Client
- Corrected the freeze notice text (`NOTIFYMSG_MAGICEFFECT_ON13`) from "Your movement decreases to 50" to "Your movement decreases by 25%", so the message matches the client's actual frozen movement slowdown (`EntityMotion` ×1.25). Attacks are unaffected while frozen, consistent with the original.

### Versioning
- Bumped server version to 0.1.22 and client version to 0.2.48 (bug fix touching client + server; no protocol change — compatibility stays 0.2.11).

### Networking (diagnostics / hardening)
- `drain_to_queue` now logs **which** failure produced a `-1` — `SocketClosed` (peer/server dropped the connection), `SocketError` (with `WSAErr`), or `MsgSizeTooLarge` (stream desync) — instead of collapsing all three into an opaque code. The client's `Poll` close/error cases log too. (This is what pinpointed the disconnect above as a server-initiated close rather than a networking fault.)
- `on_read` dumps the raw 3-byte frame header when rejecting an oversized frame, and guards the `size < 3` unsigned underflow that previously wrapped a garbage frame size to ~4 billion. `get_rcv_data_pointer` guards the same underflow so a desynced frame can never make `*msg_size` wrap to ~`SIZE_MAX` (which a caller would try to copy and crash on).

# Delayed second drops and 5×5 boss loot scatter

### Drop system
- The tier-2 ("second") drop is now **delayed** for every NPC instead of landing the instant the mob dies. It is still *rolled* at death (while the killer is valid), but the result is queued on the corpse and *placed* when the corpse decays — reached through the existing `npc_behavior_dead` regen-timer gate. This faithfully reproduces the original game's two-stage split: gold/tier-1 gear drop immediately on the death tile, the tier-2 bonus appears a little later. Tier-1 and gold drops are unchanged (still instant). Delay length is each NPC's own `regen_time` (regular mobs ~3–10s; the five bosses are 60s).

Hellclaw and Tiger Worm do **not** scatter (matching the original) — their guaranteed second item just drops, delayed, on the exact tile.
