# Item Tiers — drop odds became a number you can read

Issue #66 (epic #36). "How often does a player see tiered gear" was not a number anywhere in the system: it is the product of a hardcoded gold chance, two `server_config.json` multipliers, a per-grade `first_drop_chance`, the gear share of whichever stage-1 drop table the monster uses, and a per-grade tier weight — spread across a C++ constant, a JSON file and two database tables. The new `dropodds` console command multiplies that chain out from the running config and prints it. Server-only; Compatibility untouched, Server 0.11.1 → **0.11.2**.

- **The report is arithmetic on live config, not a second opinion.** Every term is read at the moment the command runs — `loot_grades`, `npc_configs`, the drop tables, both drop-rate multipliers, and the boot-selected roll strategy's own `first_drop_chance` — so `reload tiers`, `reload npcs` and `reload config` show up in the next report with no restart, and the mode the server is actually running is stated on the first line.
- **The gear share of each drop table is the half nobody could see, and it dominates.** A stage-1 table is mostly potions and meat; the fraction of its weight that lands on tier-eligible gear is what turns a 10% drop chance into a 0.6% chance of gear. It is now a column per table, and the per-grade rows resolve it into a per-kill probability for a drop at all, for tiered gear, and for each of the four tiers — printed as percentages and again as "1 in N kills", because that is the shape a tuning decision is actually made in.
- **Classification asks the roller instead of restating it.** `is_tier_scope_gear` — the §1 class check plus the named-unique exclusion — moved onto the roll-strategy seam, and the tiered roll, the GM mint gate, the boot validator's drop-table sweeps and this report all call it. Three more shared moves close the same gap: `base_gold_drop_chance` / `base_secondary_drop_chance` / `apply_drop_multiplier` left `EntityManager.cpp`'s statics for its header, the guard/dummy/crop exclusion became `npc_type_never_drops` (the pipeline's own switch now calls it), and `loot_grade_config::tier_weight` is now the one place that maps a tier onto its weight column, used by the roll and the report alike. A report that disagreed with the roller would be worse than no report.
- **It is a regression net as much as a tuning tool.** #63 — every monster in the game rolling as grade 2, which made Epic unreachable and Legendary impossible — took an owner playtest of roughly 500 kills to notice; it is one glance at the `npcs` column here. Any monster whose loot grade falls outside the ladder is printed as a `NOT PRICED` line rather than folded into an excluded tally, and monsters with no drop table are counted per grade, since both silently remove a monster from the economy.
- **Numbers as the shipped data actually stands** (primary ×1.00, gold ×1.00): a boss kill yields tiered gear once in 11 kills and a Legendary once in 376; elite Legendary is one in ~32,000; vermin gear is one in ~1,690, dragged down by the 14 of 69 vermin configs that have no drop table at all. The boss figures are looser than the §8 estimate written before implementation (one Legendary per ~590 kills) because the stage-1 boss tables were curated since — Abaddon's gear share is 13.6%, not the ~8% the spec assumed. Nothing was retuned in this cycle; the point is that a retune is now a calculation.
- Usage: `dropodds` for the whole picture, `dropodds <grade>` to drill into one grade's tables and list its monsters one by one. Machine-readable `DROPODDS MODE|GRADE|SPLIT|TABLE` lines ride along, and `Server --dropodds [grade]` runs it headlessly like `rollsmoke` and `mintcheck`.
- Evidence: Windows `-Target Server` Debug green, 0 errors, 0 warnings. The reported tier splits match `rollsmoke` at 200,000 rolls per grade — grade 5 reported 35/40/22/3 against an observed 34.95/40.05/22.01/2.99, grade 4 reported 60/32/7.5/0.5 against 60.10/31.93/7.45/0.52. Abaddon's 13.5939% gear share matches the figure an independent pass measured before this cycle. Legacy mode smoked by flipping `meta.item_system` and restoring it: the tier columns blank out and the tier-split table is omitted. `mintcheck` still accepts a tier-4 Sabre and still refuses item 90 and Excalibur with their own distinct reasons, so the mint-gate split survived the refactor.
- Left for the owner: the Linux server build gate, and confirming `reload tiers` reflection interactively — a piped console session is Linux-only, so on Windows the reload path is verified structurally (`reload_tier_tables` replaces `m_tier_config` wholesale, which is the accessor the report reads) rather than by running it.

# Client crash fixed — equipping into a slot whose previous item no longer existed

An access violation in `inventory_manager::unequip_slot`, reported from a live client: double-clicking an item to equip it read item id `m_item_equipment_status[equip_pos]` and dereferenced `m_item_list[that id]` with no check that the entry was still there. Client-only; Client 0.8.1 → **0.8.2**.

- **The equip-status table could name an inventory slot that had already been emptied.** `erase_item` cleared the order table, the shortcuts, the item itself and the equipped flag — but never the equip-position table, so it relied entirely on each caller having cleared the right slot first. Three of the five callers cleared the wrong one: `HandleItemDurabilityEnd`, `HandleItemReleased` and `HandleDropItemFin_EraseItem` indexed by `m_item_list[i]->m_equip_pos`, the *instance* field, which the client never populates — `init_item_list` ignores the `equip_pos` byte the packet carries, so it reads 0 (`EquipPos::None`) for every inventory item. Those three cleared slot 0 and left the real slot pointing at an item that was then erased. Dropping an equipped item and equipping a replacement into that slot is the reported path.
- **The slot question is now answered by sweeping, not by guessing.** `release_equipment_slots(item_id)` clears every equip position naming that item and marks it unequipped, so no caller has to work out which slot the item occupied. All five network handlers use it — including the two that were already correct via `cfg->m_equip_pos`, since a single spelling is worth more here than the two saved iterations — and `erase_item` calls it itself, which is what makes the invariant hold no matter what a future caller forgets.
- **`unequip_slot` no longer trusts the table it reads.** A stale entry now clears itself and returns instead of dereferencing an empty slot, which keeps the crash impossible even if some path reintroduces a stale write. The item pointer is fetched once and reused rather than re-indexing through `m_item_equipment_status` five times, and the `equip_pos >= 11` literal is now `to_int(EquipPos::LeftFinger)` — the same spelling the two dialog boxes already use for the identical angelic-stat gate.
- **The matching unchecked write is guarded too.** `equip_item` rejected only `EquipPos::None` before indexing `m_item_equipment_status[cfg->m_equip_pos]`, so a config row carrying a position outside the 15-slot table would have written past the array. It now range-checks, taking the same "this item cannot be worn" path.
- Evidence: Windows `-Target Game` Debug green, 0 errors. `git diff` reviewed — the angelic-stat branch, the release message and the ordering of the two clears are unchanged; only the indexing changed. The fix is inherently interactive to confirm: drop or destroy an equipped item, then equip a replacement into that slot.
- Not changed: `init_item_list` still leaves the instance `m_equip_pos` at 0. Nothing reads it on the client now that the three handlers don't, so populating it would only re-arm the same trap for the next reader.

# Item Tiers — damage-over-time ticks float a number over their victim

Issue #70 (epic #36). Bleed and poison each took HP every couple of seconds and said so only in a chat line, which is why a working bleed still read as nothing happening. Both now push a floating number over the victim, visible to everyone in view, colored by which effect produced it. Third and last of the three cycles riding the single Compatibility bump **0.8.0 → 0.9.0**.

- **Neither DoT had a number, so this fixes poison too.** The ticket was written about bleed, but poison has been silent in exactly the same way since long before tiers existed — it pushed `"You took -N poison damage."` into the scrolling event list and nothing else. Both route through one new message rather than bleed getting a bespoke one.
- **Two tempting reuses were both wrong, and the design is shaped by avoiding them.** `Type::Damage`/`Type::DamageMove` already carry a damage number to nearby clients, but that path locks the movement controller, cancels casting and plays the damage animation — a bleeding player would have been interrupted every second for eight seconds. `Notify::StatusText` already draws floating text, but the client hardcodes it to `m_player->m_player_object_id`, so it can only ever render over yourself and remote victims would show nothing. The new `CommonType::DotTick` instead rides the existing type-B nearby transport (`v1` = victim object id, `v2` = amount, `v3` = kind), which is position-addressed and already reaches everyone in view — no new packet struct, no new broadcast machinery, and object ids top out at 30000 so they fit its short fields as-is.
- **The number is what was actually lost, not what the tick was worth.** Both effects have paths where the full tick does not land: poison clamps at 1 HP, and a bleed whose attacker can no longer be identified clamps at 1 HP rather than killing anonymously (the 3-D credit rule). Each exit computes the real delta, and the lethal paths send *before* the kill is resolved — `client_killed_handler` and `on_entity_killed` tear the victim down, and a killing tick deserves its number the same way an ordinary killing blow gets one.
- **Player bleed moved onto the 300 ms poll, which is what makes the retuned interval real.** `tick_bleed` settles at most one tick per call, and its catch-up clause resets to `now + interval` rather than firing a backlog — so a caller polling no faster than the bleed interval silently *drops* ticks. NPC victims have always polled at 300 ms through the NPC sweep, but player victims rode `RegenManager::process_client_tick`, which runs on the 1 s `check_client_response_time` gate. At the old 2 s interval that was invisible; at the new 1 s interval a player would have landed seven ticks instead of eight. `CGame::tick_player_bleed` now polls players on the game tick, gated on the debuff being live before the call so a non-bleeding client costs one load and a branch — the same shape the NPC sweep uses. Poison stays where it was; its interval is far coarser. The constraint is now written on `tick_bleed` itself rather than being something a caller had to infer.
- **A params-table field that had been lying for as long as it existed now tells the truth.** DoT ticks need per-kind color, and the floating-text params table already declares `m_color` per row — but the sprite-font draw path ignored it and hardcoded `Yellow2x`, so the damage rows claimed `UIDmgYellow{255,255,20}` while rendering `Yellow2x{160,160,16}`. The draw now reads `params.m_color`, and every existing sprite-font row was corrected to state the color it was already rendering, so **not one pixel changes** — `LevelUp` and `enemy_kill` included, which sit on the same branch and would otherwise have visibly brightened. `magic_cast_name` draws in its own branch against a hardcoded `Red4x`; its row now says `Red4x` too. This is what lets a DoT row simply pick green or red instead of needing a special case in the renderer.
- Poison uses `PoisonText`, already this codebase's poison green (the HUD draws a poisoned HP number in it), rather than a new constant; bleed uses `Red4x`. Both are small sprite-font numbers with the same motion as an ordinary hit so they read as damage, given a slightly longer life because a tick has no attack animation drawing the eye to it.
- Evidence: Windows `-Target All` Debug green, 0 errors, 0 compiler warnings. Server boots validator-green on the tiered dev world and a Legendary Sabre carrying the bleed line mints legal via `mintcheck`. /simplify applied inline: `RegenManager.cpp`'s `StatusEffectManager.h` include went dead when the bleed tick moved out and is deleted. The visual half is inherently interactive and remains the owner's gate — a bleed tick seen from a **second** client over a remote victim is the check that matters, since that is exactly what the `Notify::StatusText` trap would have broken.

# Item Tiers — the catalog packet finishes its presentation contract

Issue #65 (epic #36). Three gaps in the replicated catalog, merged into one pass because they reshape the same packet struct, the same DDL, the same seed script and the same client read path — doing them separately meant reshaping the same five files three times. Second of three cycles riding the single Compatibility bump **0.8.0 → 0.9.0**; gamedata.db schema 8 → **9**.

- **Tooltip line placement became data.** Whether a modifier renders as its own tooltip line or merges into the damage / weight / durability line was a hardcoded switch on four modifier IDs in `category_for_modifier`. Every other presentation fact about a modifier — its label, its format, its display multiplier, its name word — already lived in the catalog and replicated; this one did not, so adding an inline modifier meant a client rebuild while every other presentation change was a database edit. `modifier_catalog.effect_placement` now carries it, the client renders whatever the row says, and the switch is gone. The four rows that are not standalone (Sharp and Ancient inline into damage, Light into weight, Strong into durability) are exactly what the old switch said, so tooltips are unchanged by this move.
- **The Bucket ordering key stopped being a stand-in, and `bucket_id` was the wrong candidate.** `tier_buckets.sort_order` existed, had no reader anywhere, and worked only because the seed happens to set `sort_order == bucket_id` for all nine buckets — reorder them in data and the column silently did nothing. The ticket allowed either replicating `sort_order` or declaring `bucket_id` ordinal and dropping the column; **`sort_order` wins**, because `bucket_id` is an identity and a foreign-key target from `modifier_catalog`, so reordering the tooltip must not mean renumbering it everywhere it is referenced. It is resolved onto each catalog row once at config load and rides the row, since buckets have no packet of their own; a row whose bucket is missing falls back to its `bucket_id`, which is exactly what the tooltip sorted on before.
- **Bands replicate, so the GM creator stops teaching by rejection.** `band_min`/`band_max` travel as two bytes per row — display units, and the widest seeded band tops out at 91, so a byte is honest rather than a squeeze; the fill clamps rather than truncates, so a future out-of-range band degrades to "the picker offers less than it could" and never to a wrapped window. The value picker now offers only values the server will accept. The legal *raw* window is the display band divided by the multiplier rounded **inward** at both ends, which is precisely the server's own legality boundary: Strong (multiplier 7, band 14..91) is raw 2..13, verified against `mintcheck` at all four boundaries — raw 2 and 13 legal, raw 1 (display 7) and 14 (display 98) rejected with the window named.
- **A freshly picked modifier now starts in-band instead of at zero.** Selecting a modifier reset its slot to value 0, which is out of band for every modifier that has a value at all, so the GM had to open the value picker before the mint could possibly be accepted. Both halves now seed at the band's low end. Setting the second half unconditionally is safe because `build_requested_attributes` already zeroes `value2` for non-pairs and `value` for zero-multiplier rows — that builder is the structural guard, and it is unchanged.
- **The two value-dropdown click cases collapsed into one.** They differed only in which half they wrote, and both needed the same new band offset; keeping them apart meant maintaining the offset twice. Options now start at the band's low end rather than at raw 1, so the selected row is an offset into the legal window and the anchor arithmetic follows it. `max_tiered_value = 20` is deleted — it was the widest raw value any seeded band reached, a constant standing in for data that now replicates.
- **Existing worlds migrate rather than needing a rebuild.** `effect_placement` is added by a `HasColumn`/`ALTER` following the `npc_configs.loot_grade` precedent from 2-A, defaulting to 0 (standalone), which is what every row but those four was already doing — so a pre-#65 world keeps rendering correctly until the seed sets the four. `reload tiers` recomputes the catalog hash and pushes to connected clients, so placement, ordering and band edits are all live data edits with no client rebuild and no restart, which is the ticket's second acceptance criterion doing real work.
- Evidence: Windows `-Target All` Debug green, 0 errors, 0 compiler warnings. Migration exercised on the real dev world — schema stamped 9, column added, all 40 rows defaulting to standalone, then re-seeded to exactly the four inline rows with 36 standalone. Boot validator green in tiered mode. The re-seed also confirmed the Bleed retune is genuinely carried by the seed script rather than only living in the database. Placement is spliced in by modifier ID at build time rather than widened into the 40-row table, so the four non-standalone rows stay readable instead of becoming a `0` in every tuple's thirteenth position.
- Recorded, not fixed: an out-of-range `effect_placement` value falls through to standalone rather than being rejected by the boot validator. It degrades gracefully and the seed is the only writer today, so a validator range check is worth having but is not load-bearing.

# Item Tiers — gear attribute totals reach the client, and the numbers derived from them stop lying

Issue #69 (epic #36). Equipping an item with a `+STR`-style roll changed nothing on the character screen, because nothing ever told the client. The bonuses were being applied server-side the whole time and genuinely consumed — combat damage, max HP/SP, carry weight and the equip requirement sweep all read `effective_str()` and its siblings — but the only stats-carrying packet is `PacketNotifyLevelUp`, which sends the *base* `m_str` and only fires on level-up, `ForceStatRefresh` and `SettingSuccess`. Never on equip. This is the first of three cycles riding a single Compatibility bump **0.8.0 → 0.9.0**; Server 0.11.0 → 0.11.1, Client 0.8.0 → 0.8.1.

- **A message of its own rather than a widened `ForceStatRefresh`.** Reusing the existing stats packet was the obvious move and the wrong one: its handler also zeroes `m_lu_str` and the rest of the pending level-up allocation, so every equip would have discarded a stat allocation the player had started but not yet submitted. `Notify::GearStats` carries only the six totals and touches nothing else. The base stats stay exactly what they were — the character's own, what creation, level-up and persistence read — and the gear contribution travels beside them rather than folded in, which is also what lets the display split.
- **The totals are indexed by `tier_attribute`, not six named fields, on both sides of the wire.** `CClient::m_add_attribute` was already shaped that way for a stated reason — six named members invited a silently transposed assignment — and the packet and `CPlayer::m_gear_attribute` now mirror it exactly, so filling and reading are loops rather than six chances to write `dex` into the `int` slot. They are `int16` on the wire rather than `uint8`: the per-attribute aggregate cap of 20 is a value in `gamedata.db`, not a guarantee the protocol should bake in.
- **Sent from the equip recalc choke point, which is the whole point.** `calc_total_item_effect` is the one place the totals are recomputed, so the notify goes out from there, gated on the totals having actually moved — the same capture-before/compare-after shape the two Marquee speed bytes already use a few lines below. Unlike those, this goes to the wearer alone, since gear attributes are nobody else's business. The recalc that runs during login can't send it (it is gated on `m_is_init_complete`, which is still false at that point), so `init_player_data` sends one unconditionally right after flipping that flag — otherwise a character who logs in already wearing attribute gear would show nothing until the first re-equip.
- **The client's re-derived formulas were reading base stats too, which is the larger half of the bug.** The character screen and the HUD both recompute max HP, max MP, max SP and max load locally rather than being told them, and every one of those was fed `m_str`/`m_vit`/`m_int`/`m_mag` while the server's `get_max_hp` and friends were feeding themselves `effective_*()`. A `+VIT` roll therefore raised the server's ceiling while the client's bar still read full at the old maximum. `CPlayer` gains the same six `effective_*()` accessors `CClient` has, and all seven of those call sites now read them — the client mirrors the server's inputs rather than approximating them. Angelic deliberately stays its own additive channel, added where it already is, because folding it into `effective_*()` would double-count it at every one of those sites.
- **`InventoryManager`'s equip weight gate agreed with nothing.** It compared against `m_str + m_angelic_str` where the server's matching check uses `effective_str() + m_angelic_str`, so the client could refuse an equip the server would have accepted — flagged during cycle 3-C as a `NOTE for Phase 4 (MUST FIX)` and never ticketed until now. Fixed.
- **Vit and Chr stopped being second-class.** They had no angelic pendant, so they were drawn by two hand-rolled `std::format` lines beside the four stats that went through `draw_stat`. Gear rolls all six, so a `+VIT` roll would have been the one bonus that stayed invisible; they route through the same drawer now. `draw_stat` renders the gear contribution **split** — `18 (+3)`, the owner's call — rather than folded into a single total, so the player can always see what the equipment is actually giving and unequipping stays legible. Angelic keeps folding into the number as it always has.
- Evidence: Windows `-Target All` Debug green, **0 errors and 0 compiler warnings** (the 80 remaining are the cosmetic freetype/SFML LNK4099s). Linux gates run at phase exit with the other two cycles on this bump. /simplify applied inline: `draw_stat`'s two `put_aligned_string` calls collapsed to one. Declined with reasons recorded — the snapshot/compare in `calc_total_item_effect` stays in its current shape because it deliberately mirrors the adjacent speed-bytes precedent, and `CPlayer::effective_*()` stays a mirror of `CClient::effective_*()` rather than a shared mixin, since the two live in different projects over unrelated storage and the shared thing would be six one-line additions.
- Recorded, not fixed: the server's armor stat-requirement gate is internally inconsistent — the STR case reads `effective_str()` while the DEX/VIT/INT/MAG/CHR cases read their base stats, so gear STR counts toward an armor requirement and gear DEX does not. Changing it makes strictly more items equippable, which is a balance call rather than a wiring fix, so it is left as found.

# Item Tiers — Bleed retuned so it reads as a mechanic rather than as a rounding error

Data-only change, applied live with `reload tiers` while players were online — no restart, no version bump. Bleed launched at 5 damage per 2 s for 8 s, which is four ticks and **20 damage total per proc**; against the 3–15% proc band on a Legendary weapon that works out to roughly 3 DPS, and the first live wave reported it as simply not working. It now runs **25 damage per 1 s for 8 s — eight ticks, 200 damage per proc**. Sunder's constants are untouched.

- **This is a spec amendment, not a knob turn, and is recorded as one.** `PLANS/ItemTiers_Plan.md` §5 named "5 dmg per 2 s for 8 s" as Bleed's fixed launch default. The same section frames those constants as `gamedata.db` launch defaults, so retuning them is expected rather than a contract break — but the recorded number would otherwise have gone stale against the seed, so §5 is amended in place with the reasoning and the original value kept visible. `Scripts/seed_item_tiers.py` carries the new values too, so a re-seed no longer reverts the tuning.
- **The tick cadence is only exact on one of the two victim kinds, and that is now written down.** `tick_bleed` fires at most one tick per poll, and its catch-up clause resets to `now + interval` rather than firing a backlog — so a poll slower than the tick interval silently *drops* ticks instead of batching them. NPC victims are polled every 300 ms by `npc_process()`; player victims every 1000 ms by `check_client_response_time()`. At the old 2 s interval that difference was invisible. At the new 1 s interval a player victim is polled exactly at the interval and will occasionally land seven ticks instead of eight. Moving the player tick onto the faster poll is folded into #70, which is already in that code.
- Applied to the live box by updating the two `tier_settings` rows in place rather than syncing the world DB, because a full `gamedata.db` sync overwrites the `admins` table — the gotcha that silently dropped two admins on the 0.9.2 deploy. Boot validator green on reload, config pushed to the connected clients, nobody disconnected.

# Item Tiers Phase 5 — the deploy batch: identity bumps and the tiered world going live

Issue #61 (epic #36). Twenty-five cycles of Item Tiers have been sitting unpushed and undeployed behind a single Compatibility bump; this is the batch that ships all of it at once. Server 0.10.4 → **0.11.0**, Client 0.7.9 → **0.8.0**; **Compatibility stays 0.8.0**, exactly where 1-B set it — no cycle since has touched the wire, which is what allowed Phases 2 through 4 to accumulate as one deployable unit rather than as four forced client updates.

- **Server binary, client build and world DB ship together, because separately any two of them are wrong.** The tiered tables are not configuration the code carries a default for — the catalog, the bands, the curves and the loot-grade staircase live only in `gamedata.db`, and the boot validator refuses to start a tiered world whose tables disagree with the code's expectations. A binary without the DB fails the validator; a DB without the binary is unreadable schema. This is the same lesson the Apocalypse deploy taught about `MapInfo.db` and it is why §12/§14.5 wrote the single-bump rule down: the DB is the balance source of truth and it moves when the binary moves.
- **The test world boots tiered.** `meta.item_system = 'tiered'`, so monster gear drops now roll a Tier with a Common floor and no Plain gear falls off a monster; shop, blacksmith and reward gear stay Plain. The mode is a DB row and a restart, not a build flag, so #62's legacy half of the matrix runs against this same world DB without another deploy.
- **The drop-side configuration was already data-entered and re-verified rather than re-derived.** Loot grades are applied across all 117 NPCs (73 vermin / 16 standard / 15 veteran / 8 elite / 5 boss); `--stage2-scan` reports the stage-2 tables clean of tier-eligible ordinary gear, which is the same rule the boot validator enforces, so the two agree; `--legacy-pool-audit` is clean; the eleven restricted-mob Cape placements are all present; and the boss stage-1 tables carry gear to roll against (Abaddon at a 13.6% tier-gear share). The proposal CSVs those passes emit are spent artifacts, not pending work.
- **Existing characters on the test box do not survive, and that is the 1-E gate working as designed.** The account stores moved to flat tier/modifier columns at schema 7; `VerifySqliteSchemaVersion` is deliberately fail-closed with no migration path, so a schema-6 account DB is refused rather than half-read and re-saved as corrupt attribute data. The box's account DBs and `tradingpost.db` are archived aside rather than deleted, mirroring what the local dev world did at 1-E. Old clients are version-gated out at login — also expected, and the reason the client bump ships in the same batch.
- The `admins` table is restored after the `gamedata.db` sync. Syncing the world DB overwrites it, which silently dropped two admins on the 0.9.2 deploy; it is now part of the batch rather than something noticed afterwards.

# Item Tiers Cycle 4-D — GM creator dialog: catalog-driven tiered minting

Issue #60 (epic #36). The tester menu's item creator becomes mode-aware. In tiered mode it stops speaking the legacy prefix/secondary bitmask and states a whole instance instead — a Tier, exactly that many modifier slots, an upgrade and a count — with every picker filled from the catalog the server replicated at login. In legacy mode the dialog is what it was. Client-only (0.7.8 → 0.7.9); no wire change at all, since 3-G already shipped `CommonType::TesterCreateItemTiered` and the packet that carries the 15-byte attribute POD — this cycle is the sender that opcode was waiting for.

- **The pickers hold the two structural rules the catalog actually knows, and nothing more.** `min_tier` and `bucket_id` both replicate, so the modifier list for a slot offers only modifiers whose min-tier ladder the chosen Tier reaches, and a Bucket another slot already spoke for is *absent* rather than greyed — offering a pick the server must refuse is not a choice. Changing the Tier retires the slots the new Tier cannot carry, both the ones past the count and any modifier that has climbed out of range, so `count == tier` holds by construction rather than by a check. What the dialog does **not** do is impose anything the catalog cannot justify: per-class eligibility is not enforced (3-G deliberately made it a roll weighting, not a legality rule, so a GM minting a weapon line onto a helm stays a legitimate test instrument), and there is no rarity gate beyond the ladder itself.
- **Bands do not replicate, so the value picker cannot constrain — and the rejection is where a GM learns the window.** `PacketModifierCatalogEntry` carries `multiplier`, `bucket_id`, `min_tier` and the label/format strings; `band_min`/`band_max` and the per-tier windows stay server-side. The value dropdown therefore offers the full raw range in *display* units (raw × multiplier — the same units the tooltip and the server's rejection string both speak), and an out-of-band pick comes back as `modifier 10 value 1 (display 7) outside 14..91`, which names the legal window exactly. That is the acceptance criterion "server rejections surfaced to the GM" doing real work rather than being a formality. Replicating the bands so the picker could constrain them is a packet-layout change and therefore belongs to **#65**, the catalog-packet contract ticket already gated to land before Phase 5-B while the 0.8.0 bump is undeployed; noted there rather than smuggled in here.
- **The reply lands beside the pickers that caused it, not in the scrolling event list.** A mint is answered with a `NoticeMsg`, which the client drops into the event scroll — fine for "Created 1x Sabre", useless for a two-clause rejection that scrolls away while the GM is still reading the dropdown. `HandleNoticeMsg` now offers the text to the creator, but only while the creator says it is waiting for a mint reply, so the hook cannot swallow unrelated notices; the dialog renders it under the preview, green for created and red for refused. The one rule the dialog answers locally instead of by round trip is an empty slot, because `count == tier` is the invariant the pickers own and the server's version of that complaint has nothing to point at.
- **The preview is the real thing, not a description of it.** The dialog builds the attribute POD once and both the preview and the mint packet use it, so what the GM reads is exactly what the server judges. # Item Tiers Cycle 4-C — Animation scaling from the status broadcast

Issue #59 (epic #36). The two Marquee speed bytes the server has been publishing on every status broadcast since 3-D finally have a client that reads them. A cast-reduction wand now visibly shortens the Magic animation and a move-speed cape shortens the walk/run animation *and* the tile slide, for the wearer and for anyone watching them from a second client — the fields ride the shared `PlayerStatus`, so remote entities animate from the same numbers their owner does. Attack, AttackMove, Damage and DamageMove are untouched, per spec §5. Client-only (0.7.7 → 0.7.8); Compatibility stays 0.8.0, since the two bytes have been on the wire since Phase 1.

- **The scaling went in at the one place frame time is computed, so "self and remote" cost nothing.** `CMapData::object_frame_counter` already derives every visible entity's effective frame time from that entity's own tile status — it is where haste and frozen have always been applied — so reading two more bytes off the same `m_status` covers the local player and every remote player through a single edit, with no separate local-player path to keep in sync. The same property makes NPCs a no-op by construction rather than by a guard: an NPC's status arrives through `SetFromEntityStatus`, which zeroes the player-only fields, so `cast_reduction_pct` and `move_speed_pct` are structurally 0 for anything that is not a player.
- **Walk and run now call the shared pacing model instead of re-deriving it.** The client had its own additive haste/frozen frame arithmetic sitting a few lines from `hb::shared::calc::move_frame_time`, which computes exactly the same thing and which the server's anti-cheat move floor is built from. They agreed by coincidence of maintenance, not by construction — and `Player.h` has carried a comment warning that they must never drift since 3-E. The player walk/run branch calls the shared helper outright, so the client's animation and the floor that judges it are now the same expression; the NPC branch keeps the additive path, since NPC base frame times are per-type and are not what the floor measures. Verified equivalent before the swap: `haste_frame_bonus` is `run_frame_time / 2.3` and the player run frame time *is* `run_frame_time`, so the two forms were already identical term for term.
- **The tile-slide duration was a third copy of the same constants, and is now none.** `MovementTiming::WALK_DURATION_MS`/`RUN_DURATION_MS` restated 560 and 312 as literals next to `hb::shared::balance`, which derives both, and next to the anti-cheat floor, which consumes both — the exact drift hazard 3-E left a note about. `EntityMotion::get_duration_for_action` routes Move and Run through `move_interpolation_time` and the two literals are deleted rather than re-derived, which is also what makes move speed reach the slide: the interpolation is what the quick-actions unlock measures at 95% progress, so scaling only the animation would have left the player's command cadence on the old timing. `DAMAGE_MOVE`/`ATTACK_MOVE` stay literals on purpose — attack and damage displacement are not locomotion and move speed must never touch them. Their haste/frozen factors moved from `* 0.7f` / `* 1.25f` to the named `haste_move_duration_pct` / `frozen_move_duration_pct`; both were checked to be bit-identical at both durations (200 → 140/250, 1014 → 709/1267 under either form), so this is a naming change and not a timing one.
- **One primitive expresses the (1 − r), rather than a cast-specific helper.** The first draft added a `cast_frame_time`; the /simplify pass replaced it with `apply_speed_reduction(base_ms, reduction_pct)`, because `move_frame_time` and `move_interpolation_time` were each already open-coding the same clamp-and-floor expression inline. All three now call it, so §5's "× (1 − r)" exists once in the codebase and the clamp cannot be tightened in one place and forgotten in the other two. Cast reduction is applied *after* the mastery adjustment rather than to the raw 88 ms, so a wand shortens whatever the caster's animation actually is.
- Evidence: Windows `-Target All` Debug green, 0 errors and **0 compiler warnings** (the 160 remaining are the cosmetic freetype/SFML LNK4099s). `git diff` verified against the pre-change code to confirm no timing term was lost in the restructure. **The Linux client build has not been run this cycle** — no key access to the CI box from this session — and every acceptance criterion here is something you watch happen (a faster cast seen from a second client, a walk that does not rubber-band, attack animations unchanged), so the visual pass remains the owner's gate.
- **Recorded, not fixed — and it needs a design answer before 4-C's issue closes.** The client still carries two rival movement-pacing models, and they disagree under *haste*: 8 × 54 ms = 432 ms per tile by the frame model against 560 × 0.7 = 392 ms by the interpolation model, of which quick-actions releases the next move at 95% — 372 ms. 3-E's floor takes the `min()` of both precisely because either can gate the next move packet, and its comment said 4-C would unify them. Unifying onto the additive model slows hasted movement from 372 to 410 ms/tile — a live nerf to Haste; unifying onto the multiplicative one speeds the hasted walk animation past the original client's 54 ms/frame, which is where §5's `base × haste(0.7)` composition points but which deviates from retail's animation. The `move_tile_time` comment now states the open question instead of promising a fix that did not land.

# Item Tiers Cycle 4-B — World presentation: tier beams, colored pickup line, tint gating

Issue #58 (epic #36). A tiered drop is now visible from across the screen before anyone walks over it: every tiered ground item raises a light column in its Tier color, faint neutral for Common and brighter with rank. The pickup line renders the item name in that same color, and the sprite dye-tint channel closes in tiered mode so a tier is read from color-of-light and color-of-name rather than from a recolored icon. No broadcasts, no banners, no floating labels — spec §11 as written. Client-only (0.7.6 → 0.7.7); Compatibility stays 0.8.0, since the tier byte has ridden the ground-item and map packets since 1-C.

- **The beam is a procedural column, not a new effect — the Pick, now recorded in the plan.** The effect list exists for transient animations that run to a frame count and retire themselves; a ground item persists until someone takes it, so an effect-backed beam would need lifetime tracking against tile state, new art, and would drift out of sync every time a tile changed off-screen. `Screen_OnGame::draw_tier_beam` instead draws from the tile's own data inside the ground-item pass, which makes it self-healing by construction: the tile is the single source of truth, and a tile that stops holding a tiered item stops drawing a beam on the next frame with no bookkeeping at all. Shape is a full-height pillar: a soft ground pool, a bright tapering root, and a narrow shaft dissipating to the top of the screen, with a slow pulse, blended additively so it reads as light over whatever the tile already drew instead of as a painted rectangle. Drawn *before* the item sprite, so the item sits in front of its own light. Drawing inside the tile pass is also what makes a full-height shaft legible without a second pass: a pillar painted at this row covers the rows already drawn above it — the ones behind it — and is painted over by the rows drawn after, the ones in front, so occlusion is correct for free. All four tiers raise a pillar and the per-tier alpha ramp does the grading, so Common stays a faint neutral thread while a Legendary dominates the screen.

- **Additive light desaturates toward white, which is why the blue tier looked white.** Found in the first visual pass. `dst + src` raises every channel, so a color whose channels are all high adds *brightness* rather than *hue* — Legendary's gold reads correctly because its blue channel is 16 and it therefore barely touches that channel, while Epic's 150/160/225 raises all three nearly equally and arrives as a washed-out white indistinguishable from Common. `beam_light_color` strips 80% of the shared white component and renormalizes to full brightness, so Epic emits 72/97/254 and Rare 72/255/72, while Common — pure white, no chroma to extract — passes through untouched and stays the faint neutral §11 asks for. **The replicated tier color is not modified**: this is the light the pillar emits, a beam-local derivation, and names keep rendering in the exact color the server sent. The alpha ramp also rose `{30,55,80,110}` → `{55,110,150,195}`.
- **Stacked rectangles are why it looked pixelated, so the pillar is gradient quads now.** A filled rect has a hard one-pixel edge; the world draws at logical resolution into a `setSmooth(false)` back buffer that blits 1:1 in windowed mode, so that edge reaches the screen exactly as authored — no amount of tuning alpha fixes a shape whose sides are a step function. New primitive `IRenderer::draw_gradient_quad` takes an arbitrary quad with a per-corner color and emits one GPU-interpolated draw, so each section of the pillar is a quad pair whose centre line carries the color and whose outer corners sit at alpha 0. That buys a per-pixel falloff *across* the pillar as well as along it, and it is cheaper than what it replaced: 8 quads per pillar against ~15 rects, and against the ~45 that soft edges would have cost had they been built from rects. Like the `BlendMode` parameter added to `draw_rect_filled` earlier in this cycle, it is a general primitive rather than a beam-specific entry point.
- **`IRenderer::draw_rect_filled` gained an optional `BlendMode`** rather than the beam hand-rolling additive draws out of `draw_line`, which already had exactly that parameter — the primitive API was asymmetric, and closing that gap is cheaper than working around it. Default `Alpha`, so every existing caller is unchanged; `SFMLRenderer` is the only implementor.
- **Beam color is data; beam intensity is not, deliberately.** The column reads its color from the replicated tier-presentation table through a new `item_name_formatter::tier_row` accessor — the same lookup `apply_tier_presentation` uses, so an unreplicated row demotes to *no beam* exactly as it demotes to a plain item name, one rule for missing presentation data everywhere. The per-tier alpha ramp stays a code table: promoting it to data needs a wire field, and Phases 2–4 are wire-frozen. Recorded in the plan as a Phase-5 candidate rather than left implicit.
- **The pickup line got a colored span, not a colored line.** §11 asks for the *name* in Tier color inside "You got a {name}." — the surrounding sentence stays chat-colored. `EventEntry` therefore carries an optional `event_highlight` (offset, length, color) and the renderer splits the draw into prefix / name / suffix, measuring each run to advance. This is a general mechanism on the event list rather than a pickup-specific special case, which is what let the two lists share one implementation: `show_events` previously carried the *same* seven-case color switch twice, once per list, and both collapse into a single `event_color` table plus one line drawer. The switches had no `default`, so an unlisted color index drew nothing at all — preserved exactly, as a null color rather than an accidental fallback. The name offset is found with `rfind`, since the name is the last thing the template substitutes.
- **The tint gate closes a palette band, not a mode-shaped branch at each draw site.** Palette entries 16-21 exist for exactly one reason — they are the legacy strategy's prefix tints, written by `attribute_prefix_types.weapon_color` and by the GM mint switch — so in tiered mode `CGame::draw_item_sprite` zeroes that band and nothing else. Player and config dyes (1-15) keep working, and a legacy item minted before a mode flip stops tinting too, which is what "sprites are never tinted in tiered mode" literally says. One gate covers every icon and ground sprite in the game because that function is the single shared draw path. `worn_tint_params` needs no gate at all: worn colors are 4-bit on the wire (`Appearance.h`, `(iApprColor >> 28) & 0xF`), so the prefix band can never reach it — verified rather than assumed.

The tint-band reasoning was checked against the live data — `attribute_prefix_types.weapon_color` in `gamedata.db` is 16-21 for every prefix that tints, the single exception being prefix 10 mapping to regular dye 5, which is outside the band and therefore keeps its tint by design. **The Linux client build has not been run this cycle** — no key access to the CI box from this session — and the beams, the colored pickup line and the absence of tint are all visual, so the Phase-4 visual pass in both modes remains the owner's gate.

# Item Tiers Cycle 3-G — GM item creator (server): mode-aware minting with legality enforcement

Issue #56 (epic #36). The GM creator stops being a code path that writes whatever the client asked for and becomes a request the server *judges*. In tiered mode a mint states a Tier and up to four modifier slots and must survive the same structural audit a rolled drop does — count == tier, one modifier per Bucket, the min-tier ladder, Band/window bounds — plus the two scope rules a roll gets for free (tierable gear only, never a named unique). In legacy mode the creator behaves exactly as it did. Every mint, in either mode and from any chat venue, now writes an economy-audit line. Server-only (0.10.3 → 0.10.4); Compatibility stays 0.8.0.

- **Legality lives in the Roll-strategy seam, not in the handler.** `roll_strategy` gains `mint(item, requested)` returning an empty string on acceptance and the violation otherwise, because what a legal instance even *looks like* is precisely what the two strategies disagree about — the same reason `roll` is virtual. `RollStrategy.h` had anticipated this since 3-A ("GM minting routes here in 3-G"). The tiered implementation calls `validate_tiered_instance` rather than re-deriving the rules: that function was written in 2-D as the shared gate, deliberately mirroring the spec instead of the roll code so a roll bug cannot self-certify, and #51 left an explicit note not to re-implement it. The rollsmoke harness and the GM creator are now its two callers, which is what keeps a minted Legendary and a dropped Legendary structurally the same object.
- **Per-class `modifier_eligibility` is deliberately *not* a legality rule.** The gate's signature is class-blind by design, and §10 enumerates the structural rules without it — eligibility weights what may *roll* on a class, so a GM minting a weapon line onto a helm is a legitimate test instrument rather than an illegal item. The two rules that *are* item-shaped live in the tiered mint beside the gate call: an item outside §1 scope cannot carry a tier at all, and the `is_special_item` roster is excluded exactly as it is at roll time.
- **A tiered mint is a specification, so nothing is derived from it.** `apply_modifier_derived_stats` is not called and no dye tint is applied — mirroring `tiered_roll_strategy::roll`, per §6.5/3-C (tiered stored stats never mutate) and §11 (tiered gear never tints). - **Tiered mode refuses a legacy-shaped mint instead of quietly accepting one.** The pre-4-D creator dialog packs prefix/secondary nibbles into a bitmask; in tiered mode that request is rejected with "modifiers require a tier (1-4)" while a plain mint still works, so the interim state is honest rather than producing untiered items carrying tier-system modifiers.
- **The tiered request gets its own command id rather than more fields on the old one.** `CommonType::TesterCreateItemTiered` + `PacketCommandTesterCreateItemTiered` carry the 15-byte attribute POD; the existing `TesterCreateItem` layout is untouched and old clients are unaffected, so Compatibility stays 0.8.0. Reusing the unused `text`/`v4` tail of the existing packet was rejected on evidence: `ConcurrentMsgQueue::pop` copies only the bytes a client actually sent into a buffer it does not clear, so trailing fields of the short legacy request read **stale bytes from the previous message** — a legacy mint could have been misread as tiered. The command id sits in the first bytes, so it is the one field that is always real. Cycle 4-D fills the struct in from the dialog.
- **Every mint is logged, and rejections are logged too.** New `ItemLogAction::GmMint` on the `trade` channel carries GM, IP, quantity, position and the full instance; `format_item_info` grows a `(tier=N id:v:v2 ...)` clause when a tier is present, since it only ever printed the first two slots and an audit of a four-line Legendary needs all four. Legacy lines are byte-identical (the clause is appended, and only when a tier exists). The audit covers the chat creation venues too, not just the tester menu: `/createitem`, `/giveitem` and the bulk helper the two share. The operator-facing `[GmMint]` line on the `commands` channel is the only record of a **rejected** attempt — the interesting case when a client is crafting packets.

# Item Tiers Cycle 3-E — Speed-aware anti-cheat posture; move check downgrades to log-only

Issue #54 (epic #36). The move check stops asking "did this player cross a tile in under 200 ms" and starts asking "did this player cross a tile faster than *this* player legally can" (spec §5, drift #6). The flat-200 ms disconnect at `Game.cpp` becomes a per-player floor derived from the client's own pacing, and it **logs instead of disconnecting** — posture is a `tier_settings` row, not a build. The cast floor 3-D made per-player gets the same knob. Server-only (0.10.0 → 0.10.1); Compatibility stays 0.8.0.

- **The flat 200 ms was already disconnecting legitimate players.** A hasted run is 8 frames × 23 ms = 184 ms per tile, so every hasted runner tripped a check they could not avoid — the bug was invisible only because haste plus running is a narrow window. At the other end it was far too permissive: a walk is 560 ms per tile, so a walk-speed hack could run at 2.8× and never register. One constant cannot serve both, which is the argument for the per-player floor rather than a retuned constant.
- **The floor is the faster of the client's two unlock paths, not one of them.** This is the load-bearing detail. The client releases the next move command either on animation completion (`move_frames` × per-frame time, where haste/frozen adjust the *frame* additively — `MapData.cpp`) or, with quick actions enabled, at 95% of the interpolated slide (where haste/frozen scale the whole *duration* multiplicatively — `EntityMotion.cpp`). The two models agree with no status effects and diverge under haste: a hasted walk is 432 ms by frames but 372 ms by interpolation. A floor derived from the frame model alone lands at 367 ms against a legal 372 ms cadence — a 1.4% margin that ordinary jitter would trip, turning the grace factor into a fiction. Taking the minimum restores the intended ~17% margin uniformly across walk, run, haste, frozen and speed-geared states. Cycle 4-C unifies the client onto one model, at which point the two terms collapse into one.
- **A gap is scored against the motion that produced it.** The measured interval is the duration of the *previous* move, so `m_was_running` remembers which pacing to use. Scoring a run's 312 ms gap against the 476 ms walk floor would flag every player who stops running — the most common movement pattern in the game.
- **Posture is data because log-only is a measurement phase, not a permanent state.** `posture_move` / `posture_cast` (`log` | `disconnect`) and `move_grace_pct` are the rows 2-E already seeded; they resolve once at load into `tier_config::anticheat` so the per-packet path reads plain fields. Escalating a check once live data shows the floors are clean is a `reload tiers`, not a deploy. The boot log states the posture the server actually *resolved*, not what the DB stores — a malformed row falls back to the code default, and the difference is exactly what an operator needs to see.
- **The validator refuses a typo'd posture in both modes.** A bad value silently falling back to `log` would be harmless; falling back the other way would not, and either way the DB and the running server would disagree about a rule that disconnects players. `tier_config::parse_posture` is the single owner of the vocabulary, so the loader and the validator cannot drift on what a legal value is. `move_grace_pct` outside 1..100 is likewise fatal — 0 makes every legal move a violation, and above 100 the floor exceeds the client's own pacing and does the same.
- **Log-only removed the thing that bounded the log.** A disconnect was, incidentally, a rate limiter: one line per offender, then they were gone. Without it a persistent offender emits a security line on every move packet for the whole session, and each line takes the process-global log mutex, formats a timestamp and flushes to file and console — a stall for every other thread that logs, not just the mover. Violations are now counted on the client and logged first-then-throttled, with the running count in each line. Measuring a floor wants a rate, not ten thousand identical lines. The cast check inherits the same treatment.
- **The movement pacing math moved to `Shared/`** (`hb::shared::calc::move_frame_time` / `move_interpolation_time` / `move_tile_time`, over new `BalanceConstants.h` entries) because a server floor that disagrees with client pacing is a false-positive generator by construction. `PlayerAnim::Move`/`Run` in the client now source their frame times and frame count from those same constants, so the "8 frames × 70 ms / 39 ms" relationship has one home instead of three.
- Fixed in passing: `m_move_freq_time`, `m_magic_freq_time`, `m_attack_freq_time` and `m_is_move_blocked` were never initialized in the `CClient` constructor. A garbage `m_move_freq_time` makes the first move packet's gap arbitrary — which the check reads as a speed violation, and which under the old code was a disconnect on login.
- Evidence: Windows `-Target All` Debug green (0 errors, 0 compiler warnings — all 81 are the cosmetic freetype/SFML LNK4099s); Linux **server and client** both green on `~/hb38-ci/` with zero GCC warnings. Boot smokes green in both modes with the posture line reporting `move=log cast=log`, and the dev `gamedata.db` restored byte-identical to HEAD afterward. The posture knob is verified to flip behavior with no rebuild (`posture_move` → `disconnect` reports `move=disconnect` on the next boot). Negative tests confirm the validator refuses `posture_move='warn'`, `posture_cast='warn'` and `move_grace_pct` of 0 and 101, each with a precise message, and blocks the boot. Computed floors are checked against every status combination rather than asserted. The live checks — moving and casting at legal speeds with rolled gear and confirming a silent security channel, then injecting speed and confirming a log line with no disconnect — need a running client and are the owner's manual smoke.
- /simplify 4-agent pass applied. The load-bearing catch was the rival-pacing-model divergence above, which three of the four agents converged on from different angles and which turned out to be a real correctness problem in the floor, not a tidiness issue. Also applied: one owner for the posture vocabulary, the violation-log throttle, `PlayerAnim`'s `max_frame` derived from `balance::move_frames` instead of a literal 7 plus a comment, and the haste frame bonus named rather than re-deriving `39 / 2.3` at each site. Declined with reasons recorded: dropping `m_was_running` and always scoring against the run floor (defensible against a relabelling attacker, but it abandons the spec's per-motion floor and loses real signal during the measurement phase this cycle exists to serve); converting the constructor assignments to in-class initializers (correct direction, but `CClient` assigns several hundred fields in its constructor and five in-class exceptions would read as an accident); and unifying all four frequency checks — move, cast, and the two near-duplicate swing checks in `Game.cpp` and `CombatManager.cpp` — behind a single evaluator owning grace, posture and log format. That last one is the right generalization and is now recorded as a follow-up: as built, giving the swing checks a posture means inventing a third and fourth grace idiom, whereas with an owner it would be two rows of data.

# Item Tiers Cycle 3-D — Marquee mechanics (Sunder, Bleed, drains, cast/move speed)

Issue #53 (epic #36). The six spec-§5 Marquee behaviors stop falling through `apply_modifier_totals`' `default:` and go live server-side. **Sunder** and **Bleed** are proc-on-hit debuffs rolled per landed hit; **MP/SP drain** are always-on and deterministic; **cast-time reduction** now shortens the server's own per-player anti-speedcast floor as well as the animation; **movement speed** is summed, clamped and published. All four weapon exotics work on players and NPCs alike, and no broadcast bit was added for them — victims learn about them from notify lines, exactly as §5 specifies. The two speed fields on the status broadcast, zero since Cycle 1-C, now carry real values, so Cycle 4-C has something to scale animations from. Server-only (0.9.9 → 0.10.0); Compatibility stays 0.8.0 — the wire fields all shipped in Phase 1.

- **Every launch constant is data.** Sunder's −50 / 5 s, Bleed's 5 damage / 2 s / 8 s, and the 1500 ms cast floor come from the `tier_settings` rows 2-E seeded, resolved once at config load into `tier_config::marquee` so the proc and cast paths read plain ints rather than doing a string-keyed map lookup and a throwing parse per hit. A `reload tiers` retunes them without a restart, and an active debuff carries the delta and period it was *applied* with, so a mid-flight reload cannot retune a debuff already ticking.
- **Bleed shares nothing with poison, deliberately** (spec §5): fixed tick versus `dice(1, level)`, refresh versus blocked-while-poisoned, no poison-resist check, no Cure. A weapon may roll Poisoning *and* Bleed — they sit in different Buckets — and a victim carries both at once. Refresh extends the duration but leaves the tick cadence alone; restarting the clock on every proc would let a fast weapon refresh a bleed forever without a single tick ever landing. The tick that falls exactly on the duration boundary is settled *before* expiry is considered, so the fourth tick (8 s / 2 s, ~20 damage per proc) is not silently swallowed whenever the tick loop arrives a millisecond late.
- **A bleed tick can land the killing blow** (owner decision this cycle) — but only while its source is still identifiable. Only equipped gear carries rolled lines and only players equip, so a bleed's attacker is always a player; the handle is stored beside the attacker's name and both must still agree when the tick lands. Eight seconds is long enough for a reconnect to inherit a recycled handle, and `client_killed_handler` dereferences a Player attacker handle unguarded — so an unverifiable bleed leaves the victim at 1 HP instead of killing them anonymously. - **Drains take, they do not give** (owner decision this cycle): §5 prices them as resource denial, not sustain, so the attacker gains nothing. The stamina half goes through the existing `effect_sp_down_spot`, which means a Marquee weapon respects Firm Stamina and the invincibility slate like every other SP-drain source in the game. NPCs hold a live mana pool but have no stamina, so SP drain has nothing to take from them — recorded, not an omission. The per-hit notice line is throttled to one per 3 s per victim; the two procs are discrete events and notify every time.
- **Sunder lands where defense ratio is read, not where it is stored.** `sunder_defense_delta` is queried at hit resolution instead of being written into the victim's stat block, so expiry needs no timer and nothing can leak into a saved character. It applies *after* the back-attack halving — "−50 defense ratio" is a flat step, and applying it earlier would quietly halve the debuff too — with the existing `< 1` floor keeping a sundered target from becoming impossible to miss.

The posture stays log-only (Cycle 3-E owns the `posture_*` knobs and the move check); the violation log now carries the observed gap, the computed floor and the player's reduction, so false positives are measurable.

# Item Tiers Cycle 3-C — Effect application with Aggregate caps; equip-time stat-touchers

Issue #52 (epic #36). `ItemManager::calc_total_item_effect` stops reading two fixed slots through two hand-written switches and instead walks all four `modifiers[4]` of every equipped piece, dispatching on the catalog's `effect_id` — never on the modifier ID — so a new catalog row that reuses an existing behavior needs no code change (spec §2, the code/data line). **Aggregate caps** (spec §6.5) land with it: lines are summed across the equipped set first and applied only after the walk, so the cap clamps the *total*. The §6.5 exemption for angels, unique built-ins and hero armor needs no roster check and no mode branch — it is structural, because only rolled modifier slots enter the sums while every config-sourced bonus (`add_effect` cases, `m_item_effect_value*`) goes straight to its accumulator uncounted. The inline MC-13 and CC-20 clamps are deleted in favour of the catalog's `aggregate_cap`. Server + client (0.9.8 → 0.9.9 / 0.7.4 → 0.7.5); no Compatibility change.

- **Stat-touchers derive, stored stats never mutate** (spec §4.5), by two mechanisms chosen on cost rather than one forced everywhere. Weight (Light) and swing speed (Agile) derive at *read* — weight already has exactly one server choke point (`get_item_weight`) and swing speed has two consumers, so `CItem::get_effective_weight(light_multiplier)` and `get_effective_swing_speed()` are the whole story. Max durability (Strong/Ancient) derives at *materialization* instead: ~28 sites read `m_durability` as the max, `cur_durability` is persisted and clamped against it, and creation/repair set `cur = max`, so the effective max has to exist on the item before anything reads it. `adjust_rare_item_value` became `apply_modifier_derived_stats` — durability rider only, all four slots, dispatching on `effect_id` — and every call site already sets the baseline immediately before calling (item config, or the custom-made `special_effect_value1` override), so it is idempotent as used and never accumulates.
- **A Light regression is fixed, and the fix is the original's behavior.** Checked against the leaked 3.82 source: `CGame::_AdjustRareItemValue` (`HGServer/Game.cpp:40523`) mutates `m_wWeight` by `value*4`%, `CGame::iGetItemWeight` (`:41729`) is `m_wWeight * count` with **no** light term, and the original client (`Client/Game.cpp:15687`) just displays the server-sent weight. One application, server-authoritative. This project had *two* on the server — the stored mutation plus `get_effective_weight`, added by commit 111be26 on top of the still-live mutation — and the client had a *third* variant that used the raw stored value as a percent, ignoring Light's multiplier of 4. ### Animation from the art already in hand
First in-game test read as "paper sliding across the screen" — correctly, because every frame of a sprite was identical while its screen position interpolated, so only the position moved. Fixed without new renders: each facing already has **two** genuine poses, its own action render and the standing render, so every action now cuts between them.
- Idle now breathes. Every shipped mob does — measured silhouette change across their idle frames is dire-boar 0/2/11/18/18/11/3/0%, centaur peaking at 53%, hellhound 45%, while the griffin sat at a flat 0%. A single render cannot move limbs, so the body is stretched a few px upward from a planted baseline on a rise-and-fall arc, which reads as breathing and costs nothing. Scaling rather than shifting a region avoids a seam across the shoulders; the rect height and pivot are constant across the frames so the feet never leave the ground. Peak is ~10% — deliberately under dire-boar's 18%, whose figure comes from real limb movement, so matching it with a whole-body stretch would look rubbery.

- attack `[stand, strike, strike, stand]` — a lunge and recovery rather than a frozen talon-swipe.
- damaged `[flinch, flinch, stand, stand]`, die `[stand, collapsed, collapsed, collapsed]` — a fall instead of the corpse popping in.

Placement and stability need different references — frame 0 anchors at its bbox centre (the quadruped convention: centaur 53%, dire-boar 51%, unicorn 51%), and later frames offset by how far the *torso* centroid moved, since anchoring on the torso alone would sit a profile view at ~67% and stand the griffin off its tile. - Ruled out while diagnosing, all verified rather than assumed: shadows do render (`draw_npc_layers` → `draw_shadow`, and Griffin is not in `ShouldSkipShadow`); alpha is correctly binary (every shipped pak has exactly zero partial-alpha pixels); camera pitch is in family (griffin aspect 1.72 vs dire-boar 1.66).

# Vince the Auctioneer gets his own sprite (first AI-assisted NPC)

Vince has been shipping since the Trading Post landed, but with no art of his own — the client drew him with a stand-in built from the *player* compositor (a female body in full plate with green boots and a green cape). He now has a real pak, and the whole stand-in is gone.

### Client data
- `sprites/npcs/vince.pak`: new town-NPC pak — 8 sprites (one per facing) × 8 idle frames, 64 px tall, feet-centre pivots with william's 5 px overhang (foot anchor taken from the bottom 8% of rows, not the bbox centre, or he slides sideways as he turns). Built from a three-view pre-rendered 3D sheet (front, right profile, rear) plus mirrors for W/SW/NW; NE and SE substitute the N and E art for now. Idle animation is a synthesised 1 px head settle over the 2 s cycle.
- Pipeline notes, all learned by measuring against the shipped town NPCs:
  - **Palette** — the originals carry ~220-240 unique colours per frame (pre-rendered, not pixel art), so the 24-colour item-icon quantize flattens the face to a single tone. One shared 160-colour palette across all facings, built from opaque pixels only (feeding median-cut the background block lets it hog palette boxes).
  - **No outlines, ever.** The originals have none. The first attempt used cel-shaded illustration renders and added silhouette edge-darkening on top; the useful metric is the fraction of body pixels that are *thin dark lines* (much darker than their local neighbourhood) — originals sit at 2.9-10%, the illustration source hit 12.8%. Counting near-black pixels outright does not work: it cannot tell dark art from outlined art. Edge-darkening is off, and the source is now a 3D render that scores 5.9%.
  - **Brightness is solved, not hard-coded.** Renders arrive dark, but how dark varies per generation — two sheets of the same character came in at mean luma 42 and 56 — so a gamma tuned on one blows out the next. The lift gamma is now searched across all facings at once to land the set on 84 (tom and gandalf are 82.5, howard 85.7; william is an outlier at 143.9). The search has to include the contrast step, since PIL blends toward a grey averaged over the whole image including the transparent region, which is near-black here and pushes the body ~7 luma brighter.
  - **Lift luminance, not RGB.** The gamma runs on luma and is applied back as a per-pixel scale factor across all three channels, which leaves saturation exactly as rendered. Running it on RGB directly drags every colour toward white: an earlier pass lost saturation 0.526 → 0.463 and read as if white paint had been brushed over him. Fixed, it sits at 0.62 against the originals' 0.36-0.52.
  - **Match the originals' surface smoothness, measured as local contrast** — the mean luma step between adjacent body pixels. This is what separates a sprite that reads as a solid volume from one that reads as a flat patterned shape, and it is not the same thing as overall contrast. The shipped mobs sit at dire-boar 17.2, ogre 17.5, troll 18.8, ettin 19.1, centaur 25.5: ettin's skin is one continuous tonal sweep per muscle, so the eye integrates it into form. At the 140% unsharp inherited from Vince the griffin measured 31.6 — 65% noisier than ettin — because every feather edge survives the downscale as a hard pixel step and reads as texture rather than shape. Detail at 78 px does not stay detail; it becomes noise that flattens. Dropped to 40% unsharp, landing at 20.8.
  - **Sharpen the body, not the face.** Photorealism does not survive to a 19 px head, but sharpening it does — the unsharp mask manufactures eyes, cheekbones and beard edges the originals do not have, and the face reads as a portrait beside their suggestions of one. The mask is held off the top 28% and feathered in across the shoulders. With that in place the head measures 258 px in 60 tones (spread 44.7) against william 240/96/45.8, tom 257/99/49.0, gandalf 269/113/52.6 and howard 305/126/65.2 — i.e. less facial detail than any original, which is the bar that matters. A photoreal source still *looks* photoreal at full size; that impression does not reach the sprite.

# Worn equipment coloring: original additive-offset dye (fixes DK/DM flat-black armor)

Resolves issue #21 — the worn-equipment slice of the #2/#3 faithful-coloring workstream. Gear on in-world characters and the character select/create preview was tinted **multiplicatively** (`DrawParams::tint`), which scales each texel by `palette[color]/255` — crushing a 255 specular highlight to 40 for the Dark Knight/Mage armor (palette entry 6 = 40,40,40) and rendering it flat black. The original DDraw client (and the already-fixed inventory icons, `draw_item_sprite`) instead **add a signed offset** `clamp(src + palette[color] - palette[0])` (base = regular index 0, gray 100,100,100), which preserves highlights for the glossy dark look.

### Client
- New `CGame::worn_tint_params(color, weapon)` — the original PutSpriteRGB additive-offset dye, mirroring `draw_item_sprite`'s math so worn gear matches its icon. Weapon colors 1-9 read the weapon sub-palette (dual-palette rule); armor/shield/mantle/pants/boots/arm/helm read the regular table. Worn colors are 4-bit (0-15); color 0 = plain draw (unchanged).
- `RenderHelpers.cpp` (`draw_equip_layer`, `draw_weapon`, `draw_shield`) and the menu-preview path (`draw_object_on_move_for_menu`) now route through it. Hair keeps its extended-palette (32-47) absolute tint per #3.

### Engine (SFMLEngine)
- The additive-offset fragment shader now multiplies its result by `gl_Color` (was applying only `gl_Color.a`), and the offset draw path no longer force-overwrites the sprite color to white. Together these let night-mode darkening (and alpha) reach offset-tinted draws, so worn gear keeps dimming at night in step with the body it sits on. Backward-compatible: existing offset callers pass white RGB (a no-op multiply), and item icons (no alpha-effect) are unaffected.

### Not changed (remaining #3 follow-ups)
- Weapon/shield glare overlays and berserk glow are untouched; the original's scaled-base special-case draws (−base/2 berserk, −base/3 afterimage) are not yet replicated.

# Frozen players no longer disconnected by the swing-speed anti-hack

### Bug Fixes
- Fixed an intermittent client disconnect (seen as `Game socket drain_to_queue failed: -1`) that happened when a player was frozen — e.g. by a Frost or Nizie — and swung in quick succession during the ~5s freeze. Root cause was server-side: the swing-speed anti-hack checks inflated the *minimum* legal time between swings while `frozen` (`effective_swing += frames * (bft >> 2)`), but the client never slows attacks when frozen (only movement). So swinging at the normal rate fell under the inflated threshold, tripped the "Swing hack" / "Batch swing hack" detector, and the server called `delete_client` on that one player. Removed the `frozen` term from **both** checks — `CombatManager::check_client_attack_frequency` and the 7-attack batch check in `Game.cpp`. Haste still lowers the threshold; real speed hacks are still caught.

# Delayed second drops and 5×5 boss loot scatter

### Drop system
- The tier-2 ("second") drop is now **delayed** for every NPC instead of landing the instant the mob dies. It is still *rolled* at death (while the killer is valid), but the result is queued on the corpse and *placed* when the corpse decays — reached through the existing `npc_behavior_dead` regen-timer gate. This faithfully reproduces the original game's two-stage split: gold/tier-1 gear drop immediately on the death tile, the tier-2 bonus appears a little later. Tier-1 and gold drops are unchanged (still instant). Delay length is each NPC's own `regen_time` (regular mobs ~3–10s; the five bosses are 60s).
- **Boss loot scatter (faithful 5×5):** Wyvern, Fire-Wyvern, and Abaddon now scatter their delayed tier-2 loot across a 5×5 center-out spiral around the corpse, ported from the original `ITEMSPREAD_FIEXD_COORD` table. Each boss rolls its tier-2 table `scatter_count` times (Wyvern/Fire-Wyvern 15, Abaddon 20); the first roll keeps the one guaranteed item (skips the "nothing" slot), the rest are bonus attempts that mostly miss, so a handful of real items spread out per kill. Hellclaw and Tiger Worm do **not** scatter (matching the original) — their guaranteed second item just drops, delayed, on the exact tile.
- Scattered items only land on walkable, in-bounds tiles (`get_is_move_allowed_tile`); blocked spiral cells are skipped so loot never ends up inside a wall.

### Internals
- `spawn_npc_drop_item` gained optional `dx, dy` tile-offset parameters plus the walkability guard for offset placement; the exact corpse tile (0,0) is still placed unconditionally.
- Added `queue_pending_drop` / `spawn_pending_drops` on `CEntityManager`, and a `PendingDrop m_pending_drops[25]` / `m_pending_drop_count` buffer on `CNpc` (sized to the scatter spiral). `npc_behavior_dead` places the pending drops just before `delete_entity`.
- Added the `NpcScatterCoord[25][2]` spiral offset table to `EntityManager.cpp`.

### Data / Schema
- Added a `scatter_count INTEGER NOT NULL DEFAULT 0` column to `drop_tables` (schema-create in `EnsureGameConfigDatabase`, a self-healing `ALTER TABLE ... ADD COLUMN` migration in `LoadDropTables`, the live `Binaries/Server/gamedata.db`, and the `gameconfigs-02162026.sql` seed). Set to 15 for tables 20090/20091 (Wyvern/Fire-Wyvern) and 20 for 20092 (Abaddon); the other bosses stay 0.
- Bumped server version to 0.1.21 (server-only change; no protocol or client impact).
